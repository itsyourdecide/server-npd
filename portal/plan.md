
## Цель дня

К концу дня:

- в базе существует план `starter`;
- у каждого пользователя есть одна квота;
- новый пользователь получает её автоматически;
- авторизованный пользователь может посмотреть свои лимиты;
- Proxmox пока не затрагивается.

## 1. Зафиксировать архитектуру

- Проверить изменённые документы.
- Сделать отдельный коммит только с документацией.
- Не добавлять `.env` и незаконченный код.

Готово, когда документация закоммичена и отправлена на GitHub.

## 2. Закончить миграцию `ComputePlan`

- Добавить в миграцию начальный план `starter`.
- Указать согласованные лимиты: одна VM, два vCPU, 4 GiB RAM, 30 GiB диска.
- Применить миграцию.
- Проверить таблицу через pgAdmin.
- Проверить, что в ней ровно один план `starter`.
- Проверить Alembic: current revision, head и отсутствие необнаруженных изменений.

Готово, когда новая база автоматически получает не только таблицу, но и стартовый план.

## 3. Создать модель `UserQuota`

Продумать и реализовать:

- связь с `User`;
- связь с `ComputePlan`;
- состояние квоты: как минимум `active` и `suspended`;
- дату назначения;
- правило «у пользователя может быть только одна квота».

Пока не добавлять:

- индивидуальные overrides;
- использованные CPU/RAM;
- данные VM;
- биллинг;
- сроки действия.

Подключить модель к общему набору моделей, чтобы её видел Alembic.

Готово, когда модель импортируется и Alembic видит новую таблицу.

## 4. Создать миграцию `UserQuota`

Проверить, что Alembic правильно создал:

- primary key;
- обе внешние связи;
- ограничение допустимых статусов;
- нужный индекс;
- значение статуса по умолчанию.

Добавить backfill: существующие пользователи должны получить квоту `starter`.

Применить миграцию и проверить результат в pgAdmin.

Готово, когда у каждого существующего пользователя есть ровно одна квота.

## 5. Автоматически назначать квоту новым пользователям

Создать отдельную функцию в модуле `compute`, которая:

- находит активный план `starter`;
- сообщает об ошибке, если план отсутствует;
- создаёт `UserQuota` для нового пользователя;
- не делает `commit` самостоятельно.

Вызвать её только в ветке создания нового `User`.

Важно проверить, что пользователь, identity, квота и session создаются в одной транзакции.

Готово, когда первый вход нового пользователя создаёт одну квоту, а повторный вход не создаёт дубликат.

## 6. Сделать просмотр собственной квоты

Создать compute-router и endpoint просмотра квоты.

Он должен:

- требовать авторизацию;
- брать пользователя из `get_current_user`;
- не принимать `user_id` от браузера;
- находить его `UserQuota` и `ComputePlan`;
- возвращать статус и лимиты;
- явно сообщать о внутренней ошибке, если у пользователя нет квоты.

Подключить router к приложению.

Готово, когда авторизованный пользователь видит свой план `starter`, а неавторизованный получает `401`.

## 7. Провести ручную проверку

Проверить по очереди:

- существующий пользователь видит квоту;
- новый пользователь получает квоту при первом входе;
- повторный вход не создаёт вторую квоту;
- неактивный пользователь не получает доступ;
- анонимный запрос не видит квоту;
- у каждого пользователя в БД ровно одна строка `UserQuota`;
- нельзя записать недопустимый статус;
- удаление или отключение плана не остаётся незамеченным.

## 8. Финальная проверка и коммит

- Проверить импорт приложения.
- Проверить компиляцию Python.
- Проверить Alembic current/head/check.
- Просмотреть `git diff`.
- Убедиться, что `.env` не попал в Git.
- Закоммитить только законченный этап.
- Запушить ветку.
