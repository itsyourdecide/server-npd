## 1. Границы автоматизации

Узлы делятся на два класса.

### Постоянно включённые

- `pve01–pve10` как голосующие участники единого Proxmox-кластера;
- их Ceph OSD, MON/MGR/MDS;
- критические HA-VM;
- коммутаторы, firewall/router и monitoring;
- оборудование, необходимое для доступности хранилища.

Эти узлы не выключаются Slurm. Ceph OSD-хосты нельзя использовать как динамически отключаемые compute-узлы.

### Динамические

- ASUS Slurm nodes;

Только этот класс разрешено включать и выключать автоматически.

## 2. Приоритеты

```text
1. Безопасность людей и оборудования
2. Ceph, quorum и критические инфраструктурные VM
3. Пользовательские HA-VM
4. Интерактивные научные сервисы
5. Slurm batch-задачи
```

Потеря batch-задачи допустима только при наличии checkpoint/requeue. Потеря единственной копии данных недопустима.

## 3. Slurm Power Saving

Power saving включается после проверки IPMI, времени загрузки и поведения каждой модели узла.

Пример направления конфигурации, не готовый production-файл:

```ini
SuspendProgram=/etc/slurm/power/suspend
ResumeProgram=/etc/slurm/power/resume
SuspendTime=1800
SuspendTimeout=300
ResumeTimeout=600
SuspendRate=5
ResumeRate=5
SuspendExcNodes=pve01,pve02,pve03,pve04,pve05,pve06,pve07,pve08,pve09,pve10
```

Требования:

- compute-узлы описаны в inventory с отдельными BMC-адресами;
- IPMI-пароль не передаётся через `ipmitool -P`;
- используется password file, secret store или защищённое окружение;
- скрипт проверяет результат команды и фактическое состояние питания;
- включение ограничивается группами, чтобы не создать пусковой бросок;
- узел становится доступен только после health-check ОС, сети, времени и CephFS;
- неуспешный старт формирует alert, а не бесконечный цикл включения.

## 4. Requeue и checkpoint

`PreemptMode=REQUEUE` не гарантирует сохранность вычислений. Он только возвращает задачу в очередь.

Production-политика:

- `JobRequeue=1` задаётся централизованно, если это соответствует политике кафедры;
- приложение периодически сохраняет checkpoint в CephFS;
- повторный запуск должен быть идемпотентным;
- MPI-задача при потере узла обычно перезапускается целиком;
- невосстановимые промежуточные данные не хранятся только в `/tmp` compute-узла;
- поведение каждого класса задач тестируется на принудительном отказе.

## 5. Slurm на core Proxmox-узлах

Допускаются низкоприоритетные Slurm worker VM на `pve01-03`, но это дополнительная оптимизация, не часть первого пилота.

Ограничения:

- Proxmox остаётся единственным арбитром физической RAM;
- worker VM получает ограничение RAM и низкие CPU shares;
- критические VM имеют гарантированные ресурсы;
- ballooning и memory hotplug нельзя считать гарантированным мгновенным освобождением RAM;
- `scontrol update NodeName=... State=DRAIN` не завершает текущие задачи;
- изменение `qm set --memory` через пять секунд после `DRAIN` не является безопасным вытеснением.

Для освобождения RAM требуется отдельный оркестратор:

1. Запретить новые задачи на worker.
2. Найти текущие jobs.
3. Выполнить checkpoint/requeue по политике.
4. Дождаться освобождения allocation.
5. Остановить или уменьшить worker VM подтверждённым способом.
6. Запустить пользовательскую VM.
7. После завершения вернуть worker в пул.

До реализации и испытаний этого контроллера core-узлы используются для VM, Ceph и инфраструктуры, а Slurm работает на ASUS.

## 6. Тепловая защита

### 6.1 Слои

1. Аппаратные пороги CPU/BMC.
2. Независимый датчик температуры помещения/горячего коридора.
3. Сигнал аварии кондиционера, если доступен сухой контакт.
4. Monitoring по IPMI/Redfish.
5. Управляемые PDU для крайнего случая.

Программный guard не заменяет аппаратную защиту и не должен зависеть только от одного `pve01`.

### 6.2 Fail-safe поведение

Старая логика `нет ответа IPMI => температура 0` запрещена. Отсутствие телеметрии является отдельной аварией.

Состояния:

```text
NORMAL   — температура и телеметрия в норме
WARNING  — запрет запуска новых compute-узлов
CRITICAL — requeue/остановка batch и выключение compute по группам
UNKNOWN  — потеря датчиков/IPMI; запрет масштабирования и alert
RECOVERY — ручная проверка или выдержка hysteresis перед возвратом
```

Требования:

- разные пороги для inlet, CPU, board и HDD;
- hysteresis и выдержка времени, чтобы избежать дребезга;
- параллельный опрос BMC с общим timeout;
- контроль доли узлов без телеметрии;
- минимум два независимых источника температуры;
- уведомление до отключения, если остаётся безопасное время;
- журнал причины, выполненных команд и результата;
- ручной аварийный выключатель;
- тест на отключённом compute-стенде.

### 6.3 Порядок теплового сброса

```text
1. Запретить новые Slurm jobs и новые power-on.
2. Requeue/checkpoint batch-задачи.
3. Выключать ASUS группами с подтверждением состояния.
4. Сохранять Proxmox/Ceph, пока условия допускают их работу.
5. При угрозе PVE-оборудованию выполнить управляемое завершение VM, Ceph и узлов с сохранением quorum настолько долго, насколько это безопасно.
6. Hard power-off через PDU использовать только как последнюю защиту.
```

## 7. Электрические ограничения

До измерений нельзя фиксировать число одновременно работающих compute-узлов.

Slurm power controller должен учитывать:

- максимальную разрешённую мощность помещения;
- текущую мощность PDU;
- резерв охлаждения;
- пусковой ток;
- запрет одновременного включения всех шасси;
- ручной лимит `max_active_nodes` на первом этапе.

Цель — снять лимит после расширения электрики и охлаждения, а не считать ограничение постоянной частью архитектуры.

## 8. Безопасность BMC

- IPMI размещается в отдельном VLAN.
- Доступ разрешён только оркестратору и администраторам.
- У каждой автоматики отдельная учётная запись с минимальными правами.
- Общие пароли и `-P password` в командной строке запрещены.
- Действия power-off журналируются.
- Старые неизвестные BMC-аккаунты удаляются или блокируются после factory reset/обновления.

## 9. Порядок внедрения

1. Собрать температурные и электрические baseline без автоматики.
2. Проверить BMC каждого compute-узла.
3. Реализовать только мониторинг и alerts.
4. Добавить запрет включения при WARNING/UNKNOWN.
5. Проверить включение одного узла, затем небольшой группы.
6. Проверить штатное выключение после простоя.
7. Проверить requeue/checkpoint на тестовых задачах.
8. Провести контролируемый thermal drill без production-данных.
9. Только после этого разрешить автоматическое аварийное отключение.

## 10. Критерии готовности

- Отказ одного датчика не скрывает перегрев.
- Отказ `pve01` не отключает мониторинг всего помещения.
- Ceph-узлы никогда не попадают в Slurm suspend list.
- Команда включения/выключения имеет подтверждённый результат.
- После восстановления охлаждения compute не стартует одновременно.
- Есть ручная процедура восстановления и контакты двух администраторов.
- Все сценарии проверены на тестовой нагрузке.
