## 1. Краткое решение

Архитектура состоит из двух вычислительных слоёв:

1. **10 Supermicro** — единый Proxmox VE кластер для VM, LXC, инфраструктурных сервисов и Slurm worker VM.
2. **До 48 ASUS R21A** — bare-metal Slurm-ферма для пакетных и MPI-расчётов.

Первые три Supermicro (`pve01–pve03`) являются core-узлами: на них размещаются Ceph MON/MGR, критические HA-VM и базовые управляющие сервисы. Остальные семь (`pve04–pve10`) — полноправные участники того же Proxmox-кластера и предоставляют дополнительные ресурсы для VM/LXC и Slurm.

Общее хранилище строится на Ceph. Диски VM предоставляются через RBD, общие данные пользователей и Slurm — через CephFS. JBOD подключаются к выбранным Ceph OSD-хостам после проверки SAS HBA, кабелей и состояния дисков.

## 2. Какие требования определили выбор

- Персональные Linux VM для студентов и сотрудников.
- Контейнеры для небольших инфраструктурных сервисов.
- Автоматический перезапуск критических VM после отказа физического сервера.
- Возможность использовать свободные ресурсы Supermicro для Slurm.
- Bare-metal производительность ASUS для массовых расчётов.
- Единое распределённое хранилище для VM и научных данных.
- Управление небольшими силами: ориентировочно два администратора.
- Постепенное внедрение из имеющегося списанного оборудования.
- Возможность расширять систему без смены базовой платформы.

## 3. CERN как архитектурный ориентир

Оборудование пришло из инфраструктуры LHCb/CERN, поэтому CERN является полезным референсом по эксплуатации научных вычислительных систем. Однако копировать конкретный стек CERN один в один неправильно: CERN эксплуатирует около 10 000 серверов и 450 000 CPU cores, а более 90% вычислительных ресурсов предоставляются через private cloud на OpenStack. Это другой масштаб, штат и бюджет. [CERN Data Centre](https://home.cern/science/computing/data-centre/)

Мы переносим не названия продуктов, а проверенные принципы:

| Принцип CERN | Реализация кафедры |
|---|---|
| Private cloud для гибкой выдачи ресурсов | Proxmox VE кластер и шаблоны VM/LXC |
| Batch-система вместо ручного входа на compute nodes | Slurm queue и fair-share |
| Отдельный специализированный HPC для MPI | ASUS/InfiniBand Slurm partition |
| Централизованные точки пользовательского доступа | SSH Bastion, JupyterHub, web portal |
| Разделение cloud, batch и storage слоёв | Proxmox, Slurm и Ceph с отдельными VLAN |
| Автоматизация и максимальная загрузка ресурсов | Templates, Ansible, scheduler, monitoring |
| Распределённая вычислительная модель | Возможность позднее интегрироваться с внешними ресурсами/Grid |

### 3.1 Почему Proxmox, если CERN использует OpenStack

CERN использует OpenStack для self-service private cloud и уменьшения административных затрат при выдаче вычислительных ресурсов. [CERN: Importance of OpenStack](https://home.cern/news/news/computing/importance-openstack-cern)

Цель нашего Proxmox-слоя аналогична: выдавать VM, перераспределять ресурсы и обслуживать физические узлы единообразно. Proxmox выбран вместо OpenStack, потому что:

- кластер начинается с 3 и расширяется до 10 гипервизоров, а не тысяч;
- его реально сопровождать двум администраторам;
- KVM, HA, Ceph и VLAN доступны из одной платформы;
- OpenStack добавил бы отдельные control-plane сервисы и значительно более сложную эксплуатацию.

Это адаптация cloud-подхода CERN к масштабу кафедры, а не попытка выдать Proxmox за программный стек CERN.

### 3.2 Почему Slurm, если основной CERN Batch использует HTCondor

Основной CERN Batch Service построен на HTCondor и ориентирован на High Throughput Computing с fair-share. CERN отдельно эксплуатирует Linux HPC на Slurm для задач, которым нужны несколько узлов и MPI. [CERN Batch Service](https://batchdocs.web.cern.ch/index.html), [CERN Linux HPC access](https://batchdocs.web.cern.ch/linuxhpc/access.html)

На первом этапе кафедра использует Slurm как единую систему, потому что:

- масштаб значительно меньше CERN;
- нужны и обычные batch-задачи, и MPI;
- Slurm проще развернуть как один scheduler для смешанной учебно-научной фермы;
- он поддерживает partitions, fair-share, reservations, GRES/GPU и power saving.

Но это решение должно проверяться реальной нагрузкой. Если основным профилем станут тысячи независимых HEP/Geant4 jobs, HTCondor или DIRAC следует рассмотреть как отдельный HTC-слой. CERN прямо отмечает, что большая часть single-node workloads лучше подходит HTCondor, тогда как Slurm HPC зарезервирован для multi-node задач. [CERN: HTCondor, MPI and Slurm](https://batchdocs.web.cern.ch/mpi/index.html)

### 3.3 Какие практики CERN нельзя переносить буквально

- CERN работает 24/7 с профессиональной эксплуатационной командой и резервированной инженерной инфраструктурой.
- Его storage и network рассчитаны на иной порядок нагрузки.
- Наличие списанного оборудования CERN не гарантирует исправность дисков, вентиляторов, HBA или совместимость с современным ПО.
- Старые naming, IP и настройки бывшего владельца не должны сохраняться без проверки.
- Решение считается обоснованным не из-за происхождения серверов, а после inventory, burn-in, benchmark и controlled failure tests.

## 4. Почему Proxmox VE установлен на всех Supermicro

### 4.1 Единая платформа управления

Proxmox объединяет управление KVM VM, LXC, сетью, storage, HA, правами и миграциями в одном интерфейсе. Кластер является multi-master: управлять им можно через любой доступный узел, а решения принимаются большинством голосов, а не одним постоянным master-сервером. Proxmox рекомендует минимум три голоса для стабильного кластера. [Proxmox: Cluster](https://pve.proxmox.com/wiki/Migrate_to_Proxmox_VE#_cluster)

Это уменьшает число отдельно администрируемых платформ и позволяет применять одинаковые шаблоны, роли, firewall и обновления ко всем Supermicro.

### 4.2 VM могут использовать ресурсы всех десяти серверов

Если оставить только три PVE-узла, 70% парка Supermicro нельзя будет использовать для HA-VM и удобной миграции. Установка PVE на всех десяти сохраняет универсальность:

- пользовательские VM можно размещать с учётом свободной RAM и CPU;
- сервисы можно переносить на время обслуживания;
- некритичные VM могут работать на `pve04–pve10`;
- критические VM управляются HA и используют Ceph RBD;
- Slurm worker запускается как VM и не загрязняет базовую ОС гипервизора.

### 4.3 Изоляция Slurm от гипервизора

Slurm не устанавливается непосредственно в Proxmox host OS. На каждом выбранном Supermicro создаётся Linux worker VM. Это даёт:

- ограничение CPU и RAM;
- независимое обновление Slurm-образа;
- быстрое клонирование worker из шаблона;
- отсутствие конфликтов пакетов Slurm/CUDA/MPI с Proxmox;
- возможность остановить worker и отдать ресурсы пользовательским VM.

Цена решения — небольшие накладные расходы виртуализации и более сложная работа с low-latency устройствами. Поэтому тяжёлые MPI и специализированные расчёты остаются на bare-metal ASUS.

## 5. Цена решения: питание и quorum

Десять PVE-узлов являются голосующими участниками Corosync. Для quorum требуется большинство:

```text
10 голосов → quorum 6
```

Следствия:

- массово выключить семь PVE-узлов и оставить три нельзя — кластер потеряет quorum;
- при шести включённых узлах quorum есть, но следующий отказ его уничтожит;
- для устойчивости к одному дополнительному отказу должно работать минимум семь узлов;
- штатный production-режим предполагает работу всех десяти PVE-узлов;
- обслуживание выполняется по одному узлу с предварительной миграцией VM;
- автоматическое энергосбережение применяется к ASUS, а не к членам PVE-кластера.

Это не скрытый недостаток, а осознанный компромисс: возможность запускать HA-VM на всём парке Supermicro оплачивается их постоянной доступностью и энергопотреблением.

Если измерения покажут, что постоянная работа десяти узлов экономически невозможна, архитектурное решение нужно пересмотреть до ввода `pve04–pve10` в кластер, а не манипулировать quorum вручную.

## 6. Роли Supermicro

### `pve01–pve03`: core

- Proxmox quorum и HA;
- по одному Ceph MON;
- Ceph MGR active/standby;
- критические HA-VM;
- Bastion, Reverse Proxy, Slurm Controller, monitoring и Ansible;
- Ceph OSD после подключения JBOD;
- низкоприоритетные Slurm worker VM при наличии ресурсов.

Для небольшого и среднего Ceph-кластера обычно достаточно трёх MON; это также минимальное количество для отказоустойчивого monitor quorum. [Proxmox VE Administration Guide](https://pve.proxmox.com/pve-docs/pve-admin-guide.pdf)

### `pve04–pve10`: general compute

- полноправные участники PVE-кластера;
- пользовательские VM/LXC;
- Slurm worker VM;
- временное размещение VM при обслуживании core;
- Ceph OSD только если узел и его JBOD переводятся в постоянно включённый storage-класс.

Критические сервисы получают HA-группу с приоритетом `pve01–pve03`, но могут использовать другие узлы только после проверки их сети и доступа к Ceph.

## 7. Почему ASUS остаются bare-metal Slurm

- Плотная четырёхузловая конструкция уже ориентирована на вычисления.
- Bare-metal исключает накладные расходы и упрощает MPI/InfiniBand.
- RS724QA имеет встроенный ConnectX-2 QDR; фактическое число таких узлов проверяется инвентаризацией.
- ASUS можно включать и выключать средствами Slurm Power Saving.
- Возрастное и неоднородное оборудование не становится частью quorum и HA критических VM.
- Отказ ASUS уменьшает вычислительную ёмкость, но не останавливает управление и хранилище.

Таким образом, Supermicro дают универсальную виртуализированную платформу, а ASUS — специализированную эластичную batch-ферму.

## 8. Почему используется Ceph

> **Обновление 2026-07-02:** это обоснование сохранено как справочное, но **основным путём к HA-хранилищу сейчас выбрана ZFS-репликация**, не Ceph — см. `storage_decision_zfs_replication.md`. Причина: бюджет не покрывает нужную для Ceph выделенную 10GbE-сеть. Раздел ниже остаётся в силе как объяснение, когда и почему стоит вернуться к Ceph.

### 8.1 Общий диск для HA

Proxmox HA может перезапустить VM на другом узле, но для этого её диск должен быть доступен после отказа исходного сервера. Ceph RBD является shared storage: диск VM не привязан к локальному SSD конкретного PVE-хоста.

Ceph размещает данные по failure domains. Для replicated pool планируется `size=3`, `min_size=2`, а CRUSH failure domain — `host`, чтобы копии не оказались на дисках одного сервера. Ceph прямо поддерживает `host` как failure domain для распределения фрагментов и реплик. [Ceph: Erasure code and CRUSH failure domains](https://docs.ceph.com/en/squid/rados/operations/erasure-code/)

### 8.2 Разделение типов данных

- **RBD replicated pool** — диски критических VM.
- **CephFS** — общие каталоги, проекты и результаты Slurm.
- **Archive EC pool** — большие редко читаемые данные после проверки масштаба и failure domains.
- **PBS/внешний backup** — независимые резервные копии.

Ceph является защитой от отказа диска/узла, но не заменяет backup от удаления, ошибки администратора или аварии всей серверной.

### 8.3 Почему storage нельзя строить на 1GbE

Proxmox рекомендует минимум 10GbE, выделенный под Ceph; recovery способен мешать Corosync и вызвать потерю cluster quorum. Для плотных OSD-хостов даже 10/25GbE может стать ограничением. [Proxmox: Ceph network requirements](https://pve.proxmox.com/pve-docs/pve-admin-guide.pdf), [Ceph: Hardware recommendations](https://docs.ceph.com/en/latest/start/hardware-recommendations/)

Поэтому:

- Corosync отделяется от Ceph;
- Ceph public/client использует VLAN 60;
- Ceph replication использует VLAN 61;
- обе сети должны работать через 10GbE или быстрее;
- 1GbE используется только для пилотной функциональной проверки.

## 9. Сетевая топология

```text
Internet / University uplink
            |
       Router / Firewall
            |
          trunk
            |
      sw01 ===== sw02
       |           |
       +-- pve01 --+
       +-- pve02 --+
       +-- pve03 --+
       +-- остальные PVE и ASUS распределены между sw01/sw02
```

Два HP 3500yl используются совместно. Основные подключения compute-узлов распределяются примерно поровну, чтобы отказ одного switch отключал часть вычислительной мощности, но не весь core.

Отдельный management switch для всех BMC/IPMI является желательным расширением: двух HP недостаточно одновременно для 58 основных Ethernet-соединений и 58 отдельных BMC-портов.

## 10. Почему нужны VLAN

Таблица ниже — про *причину* сегментации (это профиль данного документа). Конкретные подсети и шлюзы — в `cluster_lab_poc_plan.md` §4.

| VLAN | Назначение | Причина изоляции |
|---:|---|---|
| 10 | Proxmox/switch management | Пользователи не должны управлять инфраструктурой |
| 20 | Corosync | Чувствительность к задержкам и критичность quorum |
| 30 | IPMI/BMC | BMC даёт полный аппаратный контроль над сервером |
| 40 | Private VM | Пользовательские VM изолированы от инфраструктуры |
| 50 | DMZ | Публичные сервисы считаются потенциально атакуемыми |
| 60 | Ceph public/client | Отделение storage I/O от management и VM LAN |
| 61 | Ceph replication | Recovery/backfill не должен мешать Corosync |
| 80 | Slurm/PXE | Единая сеть provisioning и управления compute-фермой |

Trunk несёт несколько tagged VLAN между router, switches и PVE. Access-порт передаёт один untagged VLAN обычному серверу или BMC. Совместное прохождение VLAN по trunk не разрешает им общаться: межсетевой доступ контролирует router/firewall.

## 11. Публичный доступ

- Пользовательские VM находятся в VLAN 40 и имеют только исходящий интернет через NAT.
- SSH извне проходит через HA Bastion в VLAN 50.
- Web-сервисы публикуются через HA Reverse Proxy в VLAN 50.
- Proxmox, Ceph и IPMI не публикуются в интернет.
- Администраторы используют VPN/Tailscale и отдельные персональные учётные записи.

Это сокращает внешнюю поверхность атаки: вместо десятков публичных VM открываются только контролируемые точки входа.

## 12. HA и что она реально гарантирует

При внезапном отказе PVE-хоста VM не продолжает исполняться бесшовно. HA обнаруживает отказ, блокирует опасный двойной запуск и перезапускает VM на другом доступном узле. Proxmox HA использует cluster-wide locking и watchdog/fencing для корректного восстановления гостей. [Proxmox: pmxcfs and HA recovery](https://pve.proxmox.com/pve-docs-9-beta/chapter-pmxcfs.html)

Ожидаемая модель:

- RPO хранения близок к нулю для подтверждённых Ceph-записей;
- данные, оставшиеся только в RAM приложения, могут быть потеряны;
- RTO составляет время обнаружения отказа и запуска VM на другом узле;
- application-consistent backup и UPS всё равно необходимы.

## 13. Почему не выбраны альтернативы

### Только bare-metal Linux на Supermicro

Плюсы: меньше накладных расходов, проще HPC.  
Минусы: нет единого управления персональными VM, миграции и удобной HA. Не выполняет требование использовать весь парк для VM/LXC.

### Только три PVE, остальные семь bare-metal

Плюсы: лучшее энергосбережение и простая граница ролей.  
Минусы: большая часть RAM Supermicro недоступна для HA-VM; меньше гибкости при обслуживании. Отвергнуто из-за требования использовать все Supermicro для VM.

### Виртуализировать ASUS

Плюсы: единое управление.  
Минусы: усложнение MPI/InfiniBand, участие старого оборудования в инфраструктуре, отсутствие необходимости в VM на этих узлах. ASUS выгоднее оставить специализированной Slurm-фермой.

### Хранить VM только на локальных SSD

Плюсы: простота и скорость.  
Минусы: после отказа сервера HA не получает актуальный диск VM. Локальные SSD подходят для Proxmox OS, cache и некритичных временных данных, но не как единственное storage критических VM.

## 15. Условия, при которых решение следует пересмотреть

- Электрика или охлаждение не позволяют держать минимум семь, желательно десять PVE-узлов включёнными.
- 10GbE/25GbE storage network недоступна.
- JBOD нельзя безопасно распределить по нескольким failure domains.
- Измерения показывают неприемлемую производительность Slurm worker VM.
- Реальная потребность в VM оказывается значительно ниже ожидаемой.

Архитектура считается инженерным решением только при наличии измерений и тестов. Документ объясняет выбор, но не заменяет burn-in оборудования, performance benchmark и controlled failure testing.
