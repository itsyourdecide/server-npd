# 1Вычислительный кластер кафедры - целевая архитектура

> **ARCHIVED / SUPERSEDED.** Документ отражает проектное состояние июля 2026,
> содержит устаревшие сведения о `head01`, Ceph и ходе внедрения. Актуальная
> архитектура: [docs/architecture/overview.md](../../../docs/architecture/overview.md).

Лабораторная реализация до переезда описана в `cluster_lab_poc_plan.md`. VLAN 99, двойной NAT и OPNsense VM являются временными элементами PoC, а не production-архитектурой.

## 1. Цель

Создать поэтапно расширяемый кластер кафедры, который поддерживает:

- отказоустойчивые Linux VM и контейнеры;
- научные расчёты Geant4, ROOT и Monte Carlo через HTCondor; Slurm допускается позднее для специализированных MPI/HPC-задач;
- общее хранилище для VM, рабочих данных и больших архивов;
- персональные серверные VM для студентов и сотрудников;
- публичные сервисы через контролируемый шлюз;
- GPU в будущем;
- автоматическое включение вычислительных узлов с учётом питания и охлаждения.

На первом этапе ожидаются единицы пользователей. Архитектура не должна мешать дальнейшему росту.

## 2. Подтверждённые исходные данные

### 2.1 Supermicro

- Всего 10 серверов Supermicro, включая текущий `head01`.
- `head01`/`pve01` подтверждён как X10DRI-T (не X10DRi, исправлено 2026-07-01): 2× Xeon E5-2620 v4, 512 ГБ RAM, 2× SSD около 900 ГБ, 2× встроенных 10GbE Intel X540-AT2 и отдельный IPMI. Оба HBA (внутренний SAS9305-16i и внешний SAS9305-16e) также подтверждены.
- Конфигурация остальных девяти предположительно близкая, но ещё не проверена.
- Данные на остальных серверах отсутствуют; их можно переустанавливать.
- `head01` сейчас работает на Ubuntu. Перед установкой Proxmox его конфигурацию необходимо сохранить.

### 2.2 ASUS

- До 12 шасси ASUS R21A, по четыре узла в каждом: максимум 48 вычислительных узлов.
- RS724QA имеет встроенный ConnectX-2 QDR InfiniBand на каждом узле.
- RS720QA не имеет встроенного InfiniBand.
- Точное количество RS720QA и RS724QA требуется проверить.

### 2.3 Хранилище

- Ожидается примерно 8–12 JBOD-полок, ориентир - около 10.
- Максимальная оценка - около 240 HDD по 6 ТБ, но фактическое количество и состояние неизвестны.
- Полки доступны для пилота.
- Наличие и модели SAS HBA, внешних SAS-кабелей и topology JBOD ещё не подтверждены.

### 2.4 Сеть

- Подтверждены два HP 3500yl-48G.
- Каждый предоставляет 48 гигабитных access-портов.
- 10GbE поддерживается только при наличии опционального модуля; установленные модули требуется проверить.
- Первый коммутатор сейчас использует единый VLAN 10; это временное состояние, а не целевая архитектура.
- Скорость uplink будущей серверной и порядок выдачи публичных адресов неизвестны.

## 3. Основное архитектурное решение

### 3.1 Единый кластер из десяти Supermicro

Все 10 Supermicro входят в один кластер Proxmox VE и могут запускать VM, LXC и HTCondor execute VM. Первые три узла образуют core-группу:

```text
pve01 (бывший head01) ─┐
pve02                  ├─ Proxmox quorum + HA + Ceph
pve03                  ┘
```

В Proxmox нет единственного мастера. Все десять узлов являются равноправными голосующими участниками multi-master кластера, однако `pve01–pve03` получают приоритет для критических сервисов и Ceph MON/MGR.

Эти серверы не являются потерянной вычислительной мощностью. Они одновременно запускают:

- критические и пользовательские VM;
- инфраструктурные VM/LXC;
- Ceph;
- при наличии свободных ресурсов - низкоприоритетные HTCondor execute VM.

### 3.2 Остальные семь Supermicro

`pve04–pve10` являются полноправными участниками того же Proxmox-кластера и используются для:

- пользовательских VM/LXC;
- HTCondor execute VM;
- миграции и временного размещения VM при обслуживании;
- Ceph OSD только после назначения узла в постоянно включённый storage-класс.

При 10 голосах для quorum требуется 6 узлов. Для сохранения устойчивости к ещё одному отказу должны работать минимум 7 узлов; штатно предполагается работа всех 10 Supermicro. Автоматическое массовое выключение PVE-узлов запрещено.

### 3.3 ASUS

ASUS используются как bare-metal HTCondor execute farm. Автоматизация позднее включает нужное количество узлов через IPMI и выключает их после периода простоя. При появлении специализированных MPI-задач часть ASUS может быть выделена в отдельный Slurm HPC pool. Узлы с Ceph OSD в power-saving не включаются.

## 4. Хранилище

> **Обновление 2026-07-02:** основной путь к HA для дисков VM — **ZFS-репликация** между узлами (встроена в Proxmox, не требует 10GbE), а не Ceph. Подробности и причина — `storage_decision_zfs_replication.md`. Разделы 4.2-4.4 ниже описывают Ceph-путь, он отложен (не отменён), актуален при пересмотре решения.

### 4.1 Системные диски Proxmox

Если на каждом Supermicro подтверждены два исправных SSD около 900 ГБ, они используются как ZFS mirror под Proxmox. Дополнительные SSD до инвентаризации не закупаются.

### 4.2 Пилотный Ceph (отложено, см. обновление выше)

Для пилота к каждому из трёх Proxmox-узлов подключается отдельная JBOD-полка. Начальная конфигурация:

- 3–4 проверенных HDD на полку;
- один HDD - один Ceph OSD;
- CRUSH failure domain - `host`;
- replicated pool `size=3`, `min_size=2`;
- RBD-пул для дисков HA-VM;
- CephFS для общих каталогов пользователей и batch-задач.

Реплики должны находиться на разных Proxmox-хостах. Несколько копий на дисках одной полки не защищают от отказа сервера, HBA, кабеля, питания или всей полки.

### 4.3 Классы хранения в production

Планируются логические классы:


| Класс   | Назначение                                | Защита                     |
| ------- | ----------------------------------------- | -------------------------- |
| Fast/VM | системные диски критических VM, БД        | replicated Ceph RBD        |
| General | пользовательские данные и рабочие проекты | CephFS/replicated pool     |
| Archive | большие редко читаемые научные данные     | erasure-coded pool         |
| Backup  | независимые резервные копии               | отдельная система/носитель |


Erasure coding вводится только после появления достаточного числа исправных OSD и failure domains. Профиль не выбирается до инвентаризации.

### 4.4 Большие научные данные

Сценарий непрерывного накопления около 10 ТБ в месяц поддерживается как один из профилей нагрузки, но не определяет всю архитектуру.

- системный диск VM остаётся небольшим и реплицируемым;
- большие данные записываются в CephFS или объектное хранилище, а не внутрь гигантского root-диска VM;
- для года хранения требуется около 120 ТБ полезного пространства;
- точный сырой объём зависит от выбранного erasure coding и резерва на восстановление;
- невосстановимые данные требуют независимой резервной копии: Ceph не является backup.

### 4.5 Практически нулевая потеря данных

Ceph защищает уже подтверждённые записи при отказе одного узла. Это даёт RPO, близкий к нулю, но не сохраняет данные, оставшиеся только в RAM приложения или гостевой ОС. Для критичных приложений дополнительно нужны корректный `fsync`, application-consistent backup и UPS.

## 5. Сеть

### 5.1 Принципы

- Corosync не должен конкурировать с восстановлением Ceph.
- IPMI не должен находиться в пользовательской или публичной сети.
- Пользовательские VM не должны иметь доступ к Proxmox, Ceph и BMC.
- Публичные сервисы размещаются за firewall и reverse proxy.
- Текущий единый VLAN 10 должен быть разделён перед production.

### 5.2 Целевая сегментация

Номера VLAN предварительные. Конкретные подсети `10.10.<VLAN>.0/24` и шлюзы — единой таблицей в `cluster_lab_poc_plan.md` §4 (здесь не дублируются, чтобы не расходились):


| VLAN | Назначение                                                        |
| ---- | ----------------------------------------------------------------- |
| 10   | Proxmox/switch management                                         |
| 20   | Corosync                                                          |
| 30   | IPMI/BMC                                                          |
| 40   | закрытая сеть пользовательских VM                                 |
| 50   | DMZ: reverse proxy и SSH bastion                                  |
| 60   | Ceph public/client traffic                                        |
| 61   | Ceph cluster/replication traffic                                  |
| 80   | HTCondor/PXE; позднее также отдельный Slurm HPC при необходимости |


Финальное распределение по физическим интерфейсам определяется после проверки NIC и 10GbE-модулей.

### 5.3 HP 3500yl

Два HP используются для 1GbE management, IPMI, provisioning и подключения compute-узлов. Если в них установлены подходящие 10GbE-модули, они могут обеспечить пилотную Ceph-сеть для трёх узлов. Необходимо проверить модель модулей, тип портов и доступные кабели/трансиверы.

1GbE допустим для функционального теста Ceph, но не является production-сетью хранения. Для production требуется минимум 10GbE, а потребность в 25/40GbE определяется количеством OSD и измерениями.

### 5.4 Публичный доступ

Пользовательские VM имеют свободный исходящий интернет через firewall/NAT. Входящие соединения запрещены по умолчанию.

- SSH пользователей: один публичный HA bastion, вход только по ключам, переход к VM через `ProxyJump`.
- Web-сервисы: публикация по заявке через HA reverse proxy и HTTPS.
- Proxmox, Ceph и IPMI: только административная сеть/VPN/Tailscale.
- Публичный IP может быть выдан университетом либо заменён VPS-туннелем/WireGuard.
- Домен желателен перед production, но не нужен для пилота.

## 6. VM и пользователи

### 6.1 Модель использования

- Основная гостевая ОС - Linux; Windows допускается как исключение.
- На старте VM создаёт администратор из проверенного cloud-init шаблона.
- Пользователь получает `sudo/root` только внутри своей VM.
- Пользователь не получает прав на Proxmox и чужие VM.
- Поддерживаются постоянные и временные VM с датой завершения проекта.
- Для VM задаются квоты CPU, RAM, диска и сети.

### 6.2 Научные расчёты

- Персональная VM используется для разработки, сборки и небольших тестов.
- Длительные Geant4/ROOT/Monte Carlo-задачи отправляются в HTCondor; многонодовые MPI-задачи при необходимости получают отдельный Slurm HPC pool.
- CephFS обеспечивает общий доступ к проектам и результатам.
- Графические удалённые рабочие столы не являются требованием.
- Основные интерфейсы: SSH, терминал, JupyterHub и специализированные web-сервисы.

### 6.3 Идентификация

- На пилоте используются локальные учётные записи.
- В production предусматривается LDAP/AD университета, если это будет согласовано.
- Минимум два локальных аварийных администратора сохраняются независимо от внешней авторизации.
- Общие административные пароли запрещены; нужен MFA для удалённого администрирования.

## 7. Инфраструктурные сервисы

Внутри Proxmox-кластера как HA-VM/LXC могут работать:

- SSH bastion;
- reverse proxy;
- DHCP/PXE для ASUS и новых узлов;
- HTCondor Central Manager и Submit node;
- мониторинг, журналирование и уведомления;
- Ansible/Git для конфигурации;
- JupyterHub и другие кафедральные сервисы;
- резервное копирование конфигураций.

Tailscale/WireGuard для аварийного доступа устанавливается также на Proxmox-хостах, чтобы отказ управляющей VM не отрезал администраторов.

## 8. HTCondor, опциональный Slurm и энергосбережение

- Power saving применяется к bare-metal ASUS, но не к голосующим PVE-узлам.
- Штатно постоянно включены 10 Supermicro, сеть и необходимая инфраструктура хранения.
- ASUS позднее включаются через IPMI по состоянию HTCondor queue и доступности execute nodes.
- Job requeue не считается заменой checkpoint: приложения должны сохранять прогресс.
- MPI-задачи обычно перезапускаются целиком.
- HTCondor на Supermicro запускается в низкоприоритетных execute VM и не должен вытеснять критические VM.
- Реализация автоматического освобождения RAM под VM требует отдельного оркестратора; простой `DRAIN` не завершает текущие задачи.

Документ `cluster_power_thermal_priority.md` сохраняет проект автоматики Slurm как возможного HPC-слоя; power management для основного HTCondor pool требует отдельной реализации и испытаний.

## 9. Электрика и охлаждение

Конечная цель - возможность работы всего оборудования, но внедрение выполняется поэтапно из-за бюджета.

Перед выбором кондиционера необходимо измерить:

- idle и full-load потребление одного Supermicro;
- потребление JBOD с реальными HDD;
- потребление одного ASUS-шасси;
- сетевое оборудование;
- пусковые токи и распределение по фазам/линиям.

Первая пилотная очередь охлаждения может покрывать три core-узла, используемые JBOD и ограниченную ASUS-ферму. До добавления `pve04–pve10` электрика и охлаждение должны выдерживать все 10 постоянно включённых Supermicro с запасом 20–30%. Один кондиционер является точкой отказа, поэтому до появления N+1 требуется независимый датчик температуры и автоматическое отключение ASUS-нагрузки.

## 10. Резервное копирование

Ceph защищает от отказа диска/узла, но не от удаления пользователем, ошибки администратора, вредоносного ПО или аварии всей серверной.

Production требует:

- Proxmox Backup Server или эквивалент;
- расписание backup критических VM;
- проверку восстановления;
- отдельное хранилище для уникальных научных данных;
- по возможности вторую физическую площадку или offline-копию.

## 11. Этапы внедрения

Детальный поэтапный план (Этапы A–G с шагами, стоп-критериями и текущим фактом) вынесен в единый документ **`cluster_implementation_plan.md`** — это единственный источник по порядку внедрения, чтобы не расходились копии. Здесь только карта верхнего уровня:

| Этап | Кратко |
|---|---|
| A | Инвентаризация и проектирование (`cluster_inventory_checklist.md`) |
| B | Proxmox pilot: трёхузловой кластер, ZFS, quorum, ZFS-репликация |
| C | Ceph pilot — **отложено**, см. `storage_decision_zfs_replication.md` |
| D | Базовая платформа: bastion, reverse proxy, monitoring, backup, шаблоны |
| E | Первые пользователи и персональные VM |
| F | HTCondor pilot на ASUS |
| G | Production и расширение (`pve04–pve10`, публичный uplink, LDAP/AD) |

Порядок именно **лабораторной** сборки (OPNsense VM, VLAN 99, acceptance tests) — в `cluster_lab_poc_plan.md`.

## 12. Открытые решения

- Фактическая конфигурация девяти Supermicro.
- Модели SAS HBA, кабелей и JBOD.
- Состояние и количество HDD.
- Наличие 10GbE-модулей HP и InfiniBand-коммутатора.
- Фактическое энергопотребление и охлаждение десяти постоянно включённых PVE-узлов.
- Параметры uplink и публичного адреса.
- Возможность использовать университетский LDAP/AD.
- Электрическая мощность, размеры помещения и схема охлаждения.
- Наличие отдельного backup-хранилища.
- Реальный срок хранения научных данных.

Эти вопросы не блокируют трёхузловой пилот, кроме SAS/сети, необходимых для тестового Ceph.
