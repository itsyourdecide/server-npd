# Руководство по использованию и ведению документации

Статус: current
Дата создания: 2026-09-05
Последняя проверка: 2026-09-05
Назначение: правила для всех будущих изменений документации server-npd
Источник истины для: структуры, типов документов и правил их сопровождения

## 1. С чего начинать чтение

Читать документацию нужно в таком порядке:

1. Корневой `README.md` — карта репозитория.
2. `docs/current-state.md` — последнее подтверждённое состояние и известные
   проблемы.
3. `docs/architecture/overview.md` — устройство системы и целевое направление.
4. Документ нужного сервиса в `docs/services/`.
5. Runbook в `docs/runbooks/`, если нужно выполнить операцию.
6. ADR в `docs/architecture/decisions/`, если нужно понять причину решения.
7. `docs/history/` и `evidence/` — только для расследования истории.

Нельзя восстанавливать текущее состояние только по operations log или старому
плану. История говорит, что происходило тогда, а не что работает сейчас.

## 2. Куда записывать новую информацию

| Новая информация | Куда её поместить |
|---|---|
| Изменилось живое состояние сервиса | `docs/current-state.md` и документ сервиса |
| Выполнена операция | Датированная запись в `docs/history/operations-YYYY-MM.md` |
| Появилась новая задача | `docs/project/open-issues.md` или `docs/project/roadmap.md` |
| Принято архитектурное решение | Новый ADR |
| Нужна повторяемая процедура | `docs/runbooks/` |
| Найден факт об оборудовании | `docs/inventory/hardware.md` |
| Изменился IP/VLAN | `docs/network/addressing.md` |
| Изменилось физическое подключение | Соответствующая фактическая port map |
| Получен сырой лог или снимок | Датированный каталог в `evidence/` |
| Появилась действующая конфигурация | `infra/` или Ansible, не `work/` и не Markdown |
| План или документ больше не действует | `archive/` с пометкой о замене |

Если информация подходит сразу в несколько мест, полный факт хранится только в
одном источнике истины. В остальных документах ставится ссылка и короткое
объяснение, зачем читателю туда переходить.

## 3. Обязательный заголовок активного документа

Каждый активный документ начинается с метаданных:

```text
Статус: current | draft | accepted | deprecated | superseded
Последняя проверка: YYYY-MM-DD
Назначение: один короткий ответ, за что отвечает файл
Источник истины для: конкретный вид фактов или "не является источником истины"
```

Допустимые статусы:

- `current` — описывает подтверждённое действующее состояние или процедуру;
- `draft` — обсуждается и не должен использоваться как инструкция;
- `accepted` — решение принято, обычно для ADR;
- `deprecated` — ещё применимо, но готовится замена;
- `superseded` — заменено другим документом и переносится в архив;
- `archived` — исторический документ, не используется для операций.

Для `current` обязательна дата последней проверки. Если компонент давно не
проверялся, статус не продлевается автоматически.

## 4. Правила формулирования текущего состояния

Плохо:

```text
LACP сейчас работает одним линком.
JBOD подключён.
Monitoring полностью исправен.
```

Хорошо:

```text
Последняя проверка 2026-08-11: LACP работал через Gi 0/2; Gi 0/1 был Down.
Последняя документированная проверка storage: 2026-08-07.
Monitoring health-check 2026-08-13: 11/11 targets up.
```

Слова `сейчас`, `текущий`, `работает`, `исправен` и `подключён` без даты
проверки в current-state и inventory не используются.

Если факт взят только из старой записи, писать `last documented`, а не
`verified`. Для изменения на `verified` нужна живая проверка или свежий
авторитетный снимок.

## 5. Current и target нельзя смешивать

В документах архитектуры и сети используются отдельные разделы:

```text
## Развёрнуто сейчас
## Целевое состояние
## Различия и следующие шаги
```

Планируемый узел нельзя добавлять в таблицу действующих узлов. Для него
указывается `planned`, и он хранится в target/roadmap.

Фактическая port map показывает только реальное подключение. Резерв портов и
будущая раскладка находятся в target port plan.

## 6. Правила для истории

Историческая запись:

- имеет дату в формате `YYYY-MM-DD`;
- описывает изменение, причину, результат и ссылку на evidence;
- не используется как актуальный backlog;
- после публикации не переписывается, кроме исправления явной опечатки;
- хранится в хронологическом порядке от старых записей к новым.

Рекомендуемый шаблон:

```markdown
### YYYY-MM-DD — компонент — краткое изменение

Причина: ...

Изменено:

- ...

Проверка:

- ...

Результат: ...

Evidence: [ссылка](...)
```

Если после операции осталась задача, она создаётся в `open-issues.md` и в
истории указывается её идентификатор. Слово `Открыто:` без отдельной backlog
записи не используется.

## 7. Правила для roadmap и открытых задач

Каждая задача содержит:

```text
ID
Статус: next | planned | blocked | deferred | done
Приоритет: P0 | P1 | P2
Причина
Критерий готовности
Зависимости/блокеры
Ссылка на подтверждение выполнения
```

Завершённая задача не удаляется немедленно: она перемещается в короткий раздел
`Done` текущего периода, а затем уходит в history. Старые планы на отдельную
сессию не остаются в корне репозитория.

## 8. Правила для ADR

ADR фиксирует решение, а не пошаговую инструкцию. Имя:

```text
NNNN-короткое-название.md
```

Структура:

```text
Статус
Дата
Контекст
Рассмотренные варианты
Решение
Последствия и ограничения
Условия пересмотра
Что заменяет / чем заменён
```

При смене решения старый ADR не переписывается. Он получает статус
`superseded` и ссылку на новый ADR.

## 9. Правила для runbook

Каждый runbook обязан содержать:

- назначение и область действия;
- уровень воздействия и ожидаемый простой;
- prerequisites;
- точные цели команд;
- резервный канал доступа;
- стоп-критерии;
- процедуру rollback;
- проверки результата;
- `Last tested`;
- ссылку на конфигурацию, но не её случайную копию в тексте.

Опасная команда не должна появляться в обзорной архитектуре или current-state.
Она хранится только в соответствующем runbook с контекстом безопасности.

## 10. Конфигурации и evidence

Markdown объясняет систему, но не является местом хранения действующей
конфигурации.

- Ansible-managed конфигурация хранится в Ansible role/template.
- Остальная действующая конфигурация хранится в `infra/<service>/`.
- Снимок с реального узла хранится в `evidence/<component>/<date>/`.
- У снимка обязательно есть дата и происхождение.
- Снимок нельзя тихо редактировать и выдавать за живую конфигурацию.
- Единственная рабочая копия Nginx, Prometheus, PXE или systemd unit не должна
  находиться в `work/`.

## 11. Имена, язык и ссылки

- Имена файлов — lowercase kebab-case: `current-state.md`, `user-access.md`.
- Даты каталогов и записей — ISO `YYYY-MM-DD`.
- Административная документация ведётся на русском языке.
- Имена команд, параметров и продуктов не переводятся.
- Пользовательская инструкция может быть на английском, если это явно указано
  в её назначении.
- Используются настоящие Markdown-ссылки, например
  `[корневая карта](../README.md)`, а не только `` `file.md` ``.
- Ссылаться лучше на документ или устойчивый раздел, а не на номер строки.
- Для внешней технической документации указывается продукт и, по возможности,
  версия.
- Цены и объявления всегда содержат дату проверки; они не используются как
  долговечное архитектурное обоснование.

## 12. Безопасность

Никогда не коммитить в документацию или evidence:

- private SSH/WireGuard keys;
- пароли и password files;
- токены, cookies и recovery codes;
- содержимое Ansible Vault;
- Tailscale state;
- фотографии с секретами и QR-кодами доступа.

Перед добавлением снимка конфигурации проверить его на секреты. Публичный ключ
не является секретом, но его дублирование в документации без необходимости
также следует избегать.

## 13. Порядок обновления после изменения инфраструктуры

1. Изменить авторитетную конфигурацию в Ansible или `infra/`.
2. Выполнить изменение по runbook.
3. Провести проверку результата.
4. Обновить `current-state.md` и дату проверки компонента.
5. Обновить inventory, адреса или фактическую port map, если они затронуты.
6. Добавить одну историческую запись со ссылкой на evidence.
7. Закрыть или создать задачу в `open-issues.md`.
8. Проверить внутренние ссылки и отсутствие секретов.

## 14. Периодическая ревизия

Минимум раз в месяц и после крупных физических работ:

- проверить `current-state.md`;
- проверить P0/P1 open issues;
- сверить фактические port maps;
- проверить health-check команды;
- найти active-документы с просроченной `Последней проверкой`;
- проверить внешние ссылки;
- перенести выполненные разовые планы в архив;
- убедиться, что новые live-конфигурации не появились в `work/`.

## 15. Проверочный список перед commit

- [ ] Информация помещена в правильный тип документа.
- [ ] Не создан второй источник истины для того же факта.
- [ ] Current и target явно разделены.
- [ ] У текущего факта указана дата проверки.
- [ ] Историческая запись находится в правильном месяце и порядке.
- [ ] Открытая задача имеет отдельную backlog-запись.
- [ ] Все относительные ссылки работают.
- [ ] Нет паролей, private keys, токенов или recovery data.
- [ ] Действующая конфигурация находится в Ansible/`infra`, а не только в
      Markdown или `work/`.
- [ ] Устаревший документ помечен и архивирован, а не оставлен в активной
      навигации.

Запустить автоматическую проверку из корня репозитория:

```bash
python3 scripts/check-docs.py
```

Та же проверка запускается GitHub Actions для каждого push и pull request.
Изменение с битой ссылкой, неверной хронологией или активным Markdown-файлом в
корне не должно объединяться до исправления.

## 16. Главный принцип

Один факт — один источник истины. Остальные документы либо ссылаются на него,
либо фиксируют историческое состояние с датой. Если невозможно понять, является
ли утверждение текущим, планируемым или историческим, документ требует
исправления до следующего инфраструктурного изменения.
