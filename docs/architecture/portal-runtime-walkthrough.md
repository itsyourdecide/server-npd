# Portal: подробная карта работающего кода

Статус: описание реализации FastAPI в `portal/` на 2026-09-30. Это не
проектный план и не обещание, что все сценарии уже проверены на реальном
Proxmox. Если код и этот текст расходятся, первичен код; расхождение нужно
исправить в документации.

ошибок и причина разделения ответственности. Можно начать с любого потока:

   от открытия сайта до `get_current_user()` и проверки POST.
2. [Квоты и SSH-ключи](portal-runtime/02-compute-ssh-keys.md) — как новый
   пользователь получает план, как считаются ресурсы и откуда VM берёт ключ.
3. [Запросы на создание и управление VM](portal-runtime/03-vm-requests.md) —
   HTML/API → сервис → две записи в БД; отдельно разобраны start, shutdown,
   stop, reboot и delete.
4. [Очередь операций и worker](portal-runtime/04-operation-worker.md) —
   от `Operation(pending)` до подтверждённого результата, включая сбои между
   PostgreSQL и Proxmox.
5. [Адаптеры и Proxmox API](portal-runtime/05-proxmox-adapters.md) —
   интерфейс, fake, HTTP-адаптер, клиент, проверка «это наша VM».
6. [База, миграции, тесты и ограничения](portal-runtime/06-data-testing.md) —
   связи таблиц, `flush`/`commit`, конфигурация, способы проверки и открытые
   ограничения реализации.

## Три процесса, а не три приложения

```text
Browser
  │  HTML-форма или JSON API
  ▼
FastAPI web ──OIDC──> Keycloak
  │
  │ SQL: User, Session, Quota, VM, Operation
  ▼
PostgreSQL
  ▲
  │ SQL: взять Operation, сохранить результат
  │
operation worker ──ProxmoxAdapter──> Fake или HTTPS API Proxmox
```

Web и worker используют одну кодовую базу и одну БД, но запускаются отдельно.
Web **принимает намерение** пользователя и делает commit. Worker **исполняет
намерение** и меняет статус. Поэтому ответ `303` после создания/запуска VM
не означает, что Proxmox уже завершил работу.

## Путь одного действия в девяти точках

Пример — кнопка «Запустить» у остановленной VM:

1. `GET /dashboard` вызывает `get_current_user`, читает только принадлежащие
   этому `User.id` ресурсы и отдаёт HTML-форму с CSRF и idempotency UUID.
2. Браузер отправляет `POST /dashboard/vms/{vm_id}/start`.
3. `verify_csrf` проверяет, что POST связан с текущей application session;
   `get_current_user` проверяет сессию в БД.
4. `vm_start` превращает ключ из формы в UUID и вызывает
   `enqueue_vm_operation(db, user_id, vm_id, "vm.start", key)`.
5. Сервис блокирует строку **своей** VM, отклоняет недопустимый статус или
   повтор с чужим ключом и добавляет `Operation(status="pending")`.
6. HTTP-обработчик делает commit и отвечает `303` на `/dashboard#vms`.
7. `operation_worker.run_once` под блокировкой берёт операцию и сохраняет
   маркер `dispatching`; транзакция закрывается до вызова Proxmox.
8. Адаптер запускает VM, возвращает задачу провайдера или сообщает, что
   результат уже достигнут. Worker сохраняет UPID, опрашивает задачу либо
   сверяет состояние после неоднозначного ответа.
9. Только после подтверждения worker ставит `Operation.status="succeeded"`
   и `VirtualMachine.status="running"`.

Для создания VM путь длиннее: перед worker выполняются проверки квоты и
SSH-ключа, а worker проходит `clone → configure → resize → start`.

## Что означают повторяющиеся слова

| Термин | В этом проекте |
|---|---|
| Аутентификация | Keycloak подтверждает личность; Portal проверяет выданную application session. |
| Авторизация | Сервис решает, может ли данный `User.id` работать с данным объектом. |
| `User.id` | Постоянный внутренний владелец, не email и не Proxmox VMID. |
| `npd_session` | Случайный секрет в HttpOnly cookie; в БД хранится только hash. |
| `csrf_token` | HMAC текущей сессии для POST из браузера; не подтверждает личность сам по себе. |
| `idempotency_key` | ID логического запроса, позволяющий распознать повтор; не является секретом. |
| `VirtualMachine.status` | Состояние ресурса в модели Portal. |
| `Operation.status` | Общее состояние конкретного действия (`pending`, `processing`, `succeeded`, `failed`). |
| `Operation.phase` | Подшаг внутри действия, например `clone` или `reconcile_create_clone`. |
| `provider_vmid` | Числовой идентификатор в Proxmox; не заменяет Portal UUID. |
| `provider_task_id` | UPID асинхронной задачи Proxmox, если он известен. |
