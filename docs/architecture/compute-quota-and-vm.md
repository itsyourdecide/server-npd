# Целевая архитектура вычислительных квот и виртуальных машин

Статус: draft
Последняя редакция: 2026-09-16
Назначение: описать итоговую модель стартовой квоты, владения VM и безопасного
управления ресурсами Proxmox через Portal
Источник истины для: `ComputePlan`, `UserQuota`, `VirtualMachine`, проверки
квот и жизненного цикла VM; не является runbook развёртывания

## Основное решение

Каждый активный пользователь Portal автоматически получает небольшую
стартовую квоту. Для получения этой квоты и создания ресурсов в её пределах
не требуется заявка, отдельная регистрация в кластере или ручное одобрение.

Пользователь имеет одну учётную запись `User` на весь Portal. Квота не является
вторым аккаунтом: она только описывает разрешённый объём ресурсов. VM, SSH keys,
почтовый ящик и другие пользовательские объекты напрямую связаны с внутренним
`User.id`.

```text
User
 ├── UserQuota ──> ComputePlan("starter")
 ├── VirtualMachine[]
 ├── UserSSHKey[]
 └── Mailbox
```

Portal не создаёт VM заранее. Стартовая квота даёт право создать VM по
требованию. Это не резервирует физические CPU, RAM или storage для каждого
зарегистрированного пользователя и не расходует ресурсы на неактивные аккаунты.

## Граница между идентичностью и ресурсами

Keycloak подтверждает личность пользователя. Portal создаёт или находит
`User`, ведёт application session и принимает решения о доступе к объектам.
Proxmox не является системой пользователей Portal и не доступен пользователю
напрямую.

```text
Keycloak identity
        |
        v
Portal User.id
        |
        +---- UserQuota
        |
        +---- VirtualMachine.owner_user_id
```

Email, имя, способ входа и Proxmox VMID не используются как постоянный ключ
владельца. Владелец VM определяется только через `owner_user_id`.

Техническая Unix identity создаётся позднее только для функций, которым
действительно нужны login и numeric UID, например прямой SSH или HTCondor. Она
не является условием существования аккаунта Portal или VM.

## Модель данных

### ComputePlan

`ComputePlan` является именованным набором типовых лимитов. Первая версия имеет
план `starter`. Лимиты хранятся явными колонками, а не произвольным JSON:

```text
name
max_vms
max_running_vms
max_total_vcpus
max_total_memory_mb
max_total_storage_gb
is_active
```

План не является платным тарифом и не требует биллинга. Он позволяет одинаково
назначать и изменять базовую политику для новых пользователей.

### UserQuota

`UserQuota` хранит назначение плана конкретному `User` и при необходимости
индивидуальные переопределения лимитов:

```text
user_id
compute_plan_id
status
optional limit overrides
created_at
updated_at
```

У одного пользователя существует не более одной активной вычислительной квоты.
Статус позволяет оператору приостановить создание и запуск ресурсов без
удаления аккаунта и данных пользователя.

Стартовый план назначается автоматически при создании нового `User`. Для уже
существующих пользователей он назначается отдельной идемпотентной миграцией
данных или при первом обращении к вычислительному разделу.

### VirtualMachine

`VirtualMachine` является записью Portal о пользовательском ресурсе:

```text
id
owner_user_id
status
requested_vcpus
requested_memory_mb
requested_storage_gb
image_id
provider_vmid
provider_node
created_at
updated_at
```

`provider_vmid` появляется после успешного обращения к Proxmox. До этого
Portal использует собственный UUID как постоянный identifier операции. Browser
не выбирает произвольный Proxmox node, VMID, API path, privilege, VLAN или
cloud-init fragment.

Проект не обязателен для персональной VM. Если позднее появятся общие ресурсы,
добавляются `Project`, membership и явный владелец типа project; это не меняет
модель личного аккаунта.

## Стартовая квота

Предварительная безопасная конфигурация плана `starter`:

```text
max_vms: 1
max_running_vms: 1
max_total_vcpus: 2
max_total_memory_mb: 4096
max_total_storage_gb: 30
GPU: недоступен
public IP: не выдаётся автоматически
images: только allowlist утверждённых templates
```

Эти числа не являются окончательной эксплуатационной ёмкостью. Перед
production rollout необходимо измерить свободные CPU, RAM и ZFS storage на
каждом активном узле, зарезервировать ресурсы инфраструктурных VM, определить
допустимый CPU overcommit и число одновременно активных пользователей.

На текущем кластере объём установленной RAM сам по себе не определяет
безопасную квоту: shared storage недоступен, диски VM находятся на локальном
ZFS, а служебная нагрузка распределена по узлам неравномерно.

## Правила учёта

Для первой версии используются простые и предсказуемые правила:

- `max_vms` включает все VM, кроме окончательно удалённых;
- vCPU и RAM учитываются для всех существующих VM, включая остановленные;
- storage учитывается, пока существует диск;
- ресурсы резервируются уже при принятии операции создания и статусе
  `pending`;
- остановка VM не освобождает квоту;
- квота освобождается только после подтверждённого удаления VM или
  окончательного провала provisioning с освобождением резерва.

Состояние VM в Proxmox периодически сверяется с записью Portal. Portal не
считает локальную запись безусловной истиной о фактическом состоянии
инфраструктуры.

## Персональная квота и ёмкость кластера

Персональная квота и реальная доступность кластера проверяются отдельно:

```text
requested resources <= remaining user quota
AND
requested resources <= safe available cluster capacity
```

Квота является разрешением, а не физической резервацией. Пользователь может
иметь свободный личный лимит, когда кластер временно не способен разместить
новую VM.

При отсутствии глобальной ёмкости операция переходит в `pending_capacity` и
показывает пользователю понятную причину. Она не должна бесконечно повторяться
без backoff, срока ожидания и видимости для оператора.

## Создание VM и конкурентный доступ

Создание проходит следующим образом:

```text
user submits allowed VM parameters
        |
        v
transaction locks UserQuota
        |
        +---- validate quota and policy
        +---- reserve requested resources
        +---- create VirtualMachine(status=pending)
        +---- enqueue idempotent operation
        |
        v
operation worker calls Proxmox adapter
        |
        +---- pending -> provisioning -> running|stopped
        +---- temporary capacity issue -> pending_capacity
        +---- permanent failure -> failed + release reservation
```

Блокировка квоты и создание записи VM выполняются в одной PostgreSQL
transaction. Это не позволяет двум одновременным запросам использовать один и
тот же остаток квоты.

Operation worker работает от отдельного service account с минимальными
правами. HTTP request не ждёт окончания клонирования VM. Каждая операция имеет
idempotency key, ограниченное число попыток и отдельную сверку результата.

## Жизненный цикл VM

Минимальные состояния:

```text
pending
pending_capacity
provisioning
running
stopped
failed
deleting
deleted
```

Разрешённые переходы выполняет application service, а не произвольный router
или generic admin. Операции start, stop и delete разрешены только владельцу VM
или явно уполномоченному оператору.

Удаление считается завершённым и освобождает квоту только после подтверждения,
что ресурс и связанные диски удалены в Proxmox. Неоднозначный сетевой сбой не
должен создавать вторую VM или преждевременно освобождать лимит.

## Авторизация

Любая пользовательская выборка VM фильтруется по `owner_user_id` из текущей
application session. Переданный browser `user_id` не определяет владельца.

Базовые правила:

- пользователь читает и изменяет только собственные VM;
- оператор видит и восстанавливает операции в пределах своей роли;
- admin управляет планами и индивидуальными overrides;
- изменение квоты, принудительная остановка и удаление получают audit event;
- скрытие кнопки в UI не заменяет серверную проверку permission.

Portal не выдаёт пользователю Proxmox API token и не публикует Proxmox, IPMI
или внутренние management endpoints.

## Увеличение квоты

Стартовая квота не требует заявки. Если пользователю нужно больше ресурсов,
позднее может быть добавлен `QuotaIncreaseRequest`. Такая заявка изменяет
только лимиты и не создаёт второй аккаунт или отдельный cluster access.

До реализации заявок admin может назначить проверенный индивидуальный override
через application service с обязательным audit event.

## Ограничение злоупотреблений

Автоматическая квота требует защитных ограничений, но не обязательной анкеты с
возрастом, факультетом или курсом. Минимальный набор:

- подтверждённый email;
- небольшой план `starter`;
- rate limit на создание и управление VM;
- возможность приостановить квоту пользователя;
- allowlist templates, сетей и размеров;
- аудит операций и alert на массовое создание аккаунтов или ресурсов.

Если публичная регистрация окажется слишком доступной для злоупотреблений,
политику автоматического назначения плана можно ограничить приглашением или
доверенным email-доменом. Сам `User` и способы входа при этом не меняются.

## Retention и простой ресурсов

Первая версия не удаляет VM автоматически только из-за бездействия. До любой
автоматической остановки или удаления необходимо отдельно определить:

- критерий idle;
- срок хранения;
- число и каналы предупреждений;
- возможность продления;
- backup/restore policy;
- процедуру восстановления после ошибки.

Низкая квота storage является первой защитой от бесконтрольного роста. Политика
lease или автоматического удаления вводится только отдельным архитектурным
решением и не применяется задним числом без уведомления пользователей.

## Не входит в первую версию

- биллинг и платные тарифы;
- покупка или передача квоты;
- организация и project-level quota;
- GPU scheduling;
- пользовательские VLAN и публичные IP по требованию;
- произвольные Proxmox параметры;
- автоматическое удаление по idle timeout.
