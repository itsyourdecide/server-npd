# Выдача пользователю доступа к кластеру

- Статус: current
- Последняя проверка процедуры: 2026-09-05
- Last tested: 2026-08-28
- Назначение: создать согласованную SSH/HTCondor identity без пароля и sudo
- Источник истины для: последовательности provisioning и итоговой проверки пользователя

## Воздействие

Создаются аккаунты с одинаковым UID на `bastion01`, `condor01` и, при выборе,
ASUS execute-узлах. Простоя нет. Скрипт может создать пользовательские каталоги
на `/data`, только если storage доступен.

## Предпосылки

- получены желаемый lowercase login, назначение доступа и один публичный
  OpenSSH-ключ;
- private key, пароль и токены не копируются в репозиторий;
- [путь пользовательского доступа](../services/user-access.md) прошёл проверку;
- storage либо проверен, либо явно считается offline;
- администратор имеет доступ к `pve02`, `bastion01`, `condor01` и Ansible.

## Процедура

1. Сохранить публичный ключ во временный файл вне Git.
2. Из корня репозитория проверить справку и выполнить создание:

```bash
./scripts/create-cluster-user.py --help
./scripts/create-cluster-user.py <username> /path/to/id_ed25519.pub --execute-nodes
```

3. Если `/data` намеренно недоступно, использовать режим создания аккаунтов без
   storage. После восстановления storage выполнить для существующего
   пользователя `--storage-only`.
4. Передать пользователю только [quickstart](../users/quickstart.md), login и
   публичную точку входа; private key остаётся у пользователя.

## Проверка

```bash
./scripts/user-access-health.sh <username>
```

Также подтвердить одинаковый числовой UID на `bastion01`, `condor01` и execute
nodes, отсутствие sudo и успешный тестовый HTCondor job от имени пользователя.

## Стоп и rollback

Остановиться при существующем login с другим UID, несовпадении public key,
недоступности одного из обязательных хостов или неожиданно смонтированном
storage. Не исправлять UID вручную только на одном узле.

Автоматического удаления пользователя нет. Ошибочно выданный доступ сначала
блокируется удалением ключа на входных узлах; затем отдельной согласованной
операцией удаляются аккаунты и данные. Факт отзыва записывается в history.
