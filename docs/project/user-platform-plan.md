# План пользовательской платформы server-npd

Статус: draft
Дата создания: 2026-09-05
Последняя редакция: 2026-09-07
Живая проверка при редакции: не выполнялась; документ описывает целевую
платформу, а не развёрнутый сервис
Назначение: определить границы продукта, этапы поставки и критерии готовности
пользовательской платформы
Источник истины для: состава продукта и зависимостей между его этапами; не для
приоритетов остальной инфраструктуры и не для фактического состояния сервисов

## Как использовать этот план

Документ отвечает на вопросы «что получает пользователь» и «в каком порядке
безопасно раскрывать возможности». Техническая реализация вынесена в
[отдельный план](user-platform-implementation-plan.md). Фактическое состояние
кластера хранится в [current state](../current-state.md), а назначенные
владельцем задачи — в [open issues](open-issues.md).

Нумерация этапов описывает зависимости внутри пользовательской платформы. Она
не назначает приоритеты сетевым, аппаратным или закупочным работам. Начало
каждого этапа и состав конкретного релиза подтверждает владелец кластера.

## Исходная точка

До появления портала уже существует рабочий административный контур:

- key-only SSH-доступ через `bastion01` к `condor01`;
- ручная выдача согласованной Unix/HTCondor identity;
- HTCondor central manager и submit point на `condor01`;
- четыре execute-ноды первой ASUS-рельсы;
- Ansible, runbook'и и health-check'и для части операций.

JBOD/NFS намеренно выключены и не являются зависимостью первого релиза.
Портал не должен предполагать наличие `/data` или возвращать storage в работу.

## Цель продукта

Создать единую точку взаимодействия пользователя с кластером, через которую
можно:

- узнать правила и доступные возможности;
- запросить доступ и видеть состояние заявки;
- работать в составе проекта;
- видеть назначенные квоты и ресурсы;
- позднее просматривать и отправлять HTCondor-задания;
- запрашивать VM и другие ресурсы;
- получать уведомления и обращаться к документации.

Для оператора платформа должна давать очередь заявок, понятный процесс
согласования, журнал решений и контролируемый запуск только заранее описанных
операций.

## Первый полезный релиз

Первый MVP — это портал заявок, а не панель полного управления кластером.

В MVP входят:

- вход через выбранного OIDC-провайдера;
- профиль пользователя;
- проекты и членство в проектах;
- заявки на доступ и ресурсы;
- рассмотрение, комментарий, согласование и отклонение;
- история состояний и аудит действий;
- ручное исполнение согласованной заявки оператором;
- фиксация технического результата исполнения.

В MVP не входят:

- автоматическое создание Unix-аккаунтов или VM;
- отправка HTCondor-заданий из браузера;
- загрузка больших входных данных и хранение результатов;
- произвольный shell, ClassAd, Ansible playbook или Proxmox API request;
- прямой доступ к Proxmox, IPMI или внутренним сервисам;
- биллинг, маркетплейс ПО и сложная система квот.

Такой объём позволяет проверить реальный процесс работы с кафедрой до выдачи
веб-приложению инфраструктурных полномочий.

## Принципы

- Ручной и наблюдаемый процесс появляется раньше его автоматизации.
- Пользователь видит только свои данные и данные доступных ему проектов.
- Роль в портале сама по себе не даёт прав в ОС, HTCondor или Proxmox.
- Все значимые переходы состояния имеют автора, время и комментарий.
- Web-процесс не хранит административные credentials к инфраструктуре.
- Инфраструктурные операции выполняет отдельный worker с минимальными правами.
- Любая автоматическая операция идемпотентна и имеет безопасный повтор.
- Удаление, отзыв доступа и другие необратимые действия требуют отдельной
  политики и подтверждения.
- Портал не становится источником истины о состоянии кластера без явной
  сверки с целевой системой.
- Технология или функция не считается принятой только из-за упоминания в
  плане; спорные решения фиксируются ADR.

## Роли

| Роль | Возможности |
|---|---|
| `applicant` | заполняет профиль и подаёт заявку на доступ |
| `user` | работает со своими заявками и разрешёнными ресурсами |
| `project_lead` | управляет участниками и запросами своего проекта в пределах политики |
| `reviewer` | рассматривает заявки и оставляет решение |
| `operator` | исполняет согласованные инфраструктурные операции |
| `admin` | управляет настройками платформы и назначением ролей |

Один человек может иметь несколько ролей. Проверка прав выполняется для
каждого объекта и действия, а не только для раздела интерфейса.

## Базовый жизненный цикл заявки

```text
draft -> submitted -> under_review -> approved -> executing -> active -> closed
                         |              |           |
                         +-> rejected   +-> cancelled
                                        +-> failed
```

Переход `approved -> executing` не означает автоматизацию. В первом релизе
оператор выполняет существующий runbook вручную и затем сохраняет результат.

## Этап U0 — границы и решения

Цель: убрать решения, которые опасно принимать по ходу разработки.

Нужно подтвердить:

- кто является первой группой пользователей;
- какой OIDC/университетский identity provider используется;
- кто может назначать роли `reviewer`, `operator` и `admin`;
- где размещается портал и как к нему получают доступ;
- какие типы заявок входят в MVP;
- какие данные и аудит хранятся и как долго;
- какой канал уведомлений нужен в первом релизе;
- какие действия всегда остаются ручными.

Результат:

- приняты необходимые ADR;
- утверждены границы MVP и его критерии приёмки;
- определены владелец продукта и операторы;
- решения не подменены предположениями разработчика.

## Этап U1 — основа платформы

Цель: получить минимальный, восстанавливаемый и пока read-only по отношению к
кластеру сервис.

Состав:

- Django-приложение с server-rendered UI и HTMX там, где это полезно;
- PostgreSQL;
- вход по OIDC;
- базовые роли и deny-by-default authorization;
- TLS/reverse proxy;
- health endpoints, структурированные логи и метрики;
- резервное копирование PostgreSQL и тест восстановления;
- отдельные конфигурации development, test и production.

Готово, когда:

- пользователь может войти и выйти;
- закрытые страницы недоступны без аутентификации;
- роли проверяются сервером;
- восстановление тестовой базы подтверждено;
- у web-процесса нет credentials к Proxmox, HTCondor и ОС.

## Этап U2 — проекты и заявки: MVP

Цель: провести первую реальную заявку от пользователя до исполненного решения.

Состав:

- профиль пользователя;
- проект, участники и роли проекта;
- заявка на доступ к кластеру;
- универсальная заявка на ресурс;
- очередь рассмотрения;
- комментарии, согласование и отклонение;
- ручная фиксация начала и результата исполнения;
- история переходов и аудит;
- минимальные уведомления о смене состояния.

Готово, когда:

- новый пользователь проходит весь процесс без обмена статусами вне портала;
- оператор исполняет одобренную заявку по существующему runbook;
- пользователь не видит чужие заявки и закрытые проекты;
- каждое решение и изменение статуса попадает в аудит;
- повторная отправка формы не создаёт дубликат заявки или перехода состояния.

После U2 платформа может использоваться как первый внутренний production MVP.

## Этап U3 — публичная часть и документация

Цель: дать понятную точку входа до регистрации.

Состав:

- назначение кластера и доступные категории ресурсов;
- правила использования и порядок получения доступа;
- пользовательские инструкции и примеры;
- контакты и порядок поддержки;
- обезличенный статус сервисов, если он одобрен для публикации;
- ссылка на вход.

В публичную сборку не попадают внутренние IP, MAC-адреса, имена закрытых
узлов, административные инструкции и секреты. Этот этап можно выполнять после
U1 параллельно другим продуктовым работам, если владелец выберет его раньше.

## Этап U4 — HTCondor только для чтения

Цель: связать пользователя портала с существующей cluster identity без права
запуска операций.

Состав:

- подтверждённая связь OIDC identity, portal profile, Unix login и numeric UID;
- просмотр собственных активных и завершённых заданий;
- состояние очереди и понятное объяснение hold/error;
- просмотр разрешённой информации об использованных ресурсах;
- аудит обращений к интеграции.

Готово, когда:

- портал не показывает чужие задания;
- владелец задания определяется из авторитетной HTCondor identity, а не из
  переданного браузером параметра;
- отказ HTCondor не ломает заявки и вход в портал;
- интеграция работает без административных прав у web-процесса.

## Этап U5 — отправка шаблонных HTCondor-заданий

Цель: дать безопасный первый путь запуска job через портал.

Первая версия поддерживает только утверждённые профили с ограниченными
параметрами. Для каждого профиля задаются CPU, RAM, disk, runtime, число
экземпляров, допустимые аргументы и политика результатов.

Готово, когда:

- job в HTCondor принадлежит реальной cluster identity пользователя;
- лимиты проверяются сервером до submit;
- повтор запроса не создаёт вторую job;
- пользователь может остановить только собственную job;
- submit, remove и результат записываются в аудит;
- решение не зависит от включения JBOD и использует согласованный ограниченный
  механизм HTCondor file transfer.

Произвольные ClassAd и неограниченная загрузка файлов в этот этап не входят.

## Этап U6 — заявки на VM

Цель: формализовать процесс выдачи VM до его автоматизации.

Пользователь указывает проект, назначение, шаблон ОС, CPU, RAM, disk, сеть,
срок действия и участников. Оператор проверяет квоту и создаёт VM вручную.
Портал хранит ссылку на согласованную заявку, VMID, владельца, срок и состояние.

Готово, когда:

- каждая VM имеет проект, владельца, срок и согласованную заявку;
- ручная выдача и продление проходят через один процесс;
- превышение квоты явно блокируется;
- приближение срока окончания создаёт уведомление;
- удаление VM не выполняется порталом.

## Этап U7 — выборочная автоматизация и стабильная версия

Цель: автоматизировать только доказанные ручные процессы.

Возможные операции вводятся независимо:

1. создание cluster identity после одобрения;
2. применение членства и квот;
3. создание VM из утверждённого шаблона;
4. продление, блокировка и отзыв доступа;
5. обслуживание жизненного цикла ресурса.

Каждая операция требует отдельного технического допуска, минимальных
credentials, idempotency, проверки результата и runbook отката. Автоматизация
VM не является обязательным условием первого стабильного портала.

Версия считается эксплуатационно зрелой, когда:

- ошибки доставляются оператору;
- PostgreSQL регулярно копируется и восстанавливается на проверке;
- web и worker наблюдаемы раздельно;
- аудит нельзя менять через обычный пользовательский интерфейс;
- есть процедуры обновления, отката и отзыва credentials;
- проверены rate limits, session security и retention;
- владелец подтвердил перечень реально автоматизированных операций.

## Этапы после стабильной версии

Только после отдельного решения могут рассматриваться:

- JupyterHub или web terminal;
- пользовательские базы данных;
- каталог программного обеспечения;
- API/CLI;
- публикация наборов данных;
- интеграция с DIRAC/LHCb;
- отдельные сервисы Slurm/MPI.

Они не являются скрытой частью MVP.

## Контрольные точки

| Контрольная точка | Состав | Пользовательская ценность |
|---|---|---|
| Internal alpha | U0–U1 | безопасный вход и проверенная основа |
| Request MVP | U2 | проекты, заявки и прозрачное ручное исполнение |
| Public entry | U3 | правила и документация до регистрации |
| Compute portal | U4–U5 | просмотр и шаблонная отправка HTCondor job |
| Resource portal | U6 | управляемые заявки на VM |
| Stable platform | выбранные части U7 | только проверенная автоматизация и эксплуатационные гарантии |

Переход между контрольными точками не происходит автоматически. Решение
принимается после демонстрации результата и проверки критериев предыдущего
этапа.
