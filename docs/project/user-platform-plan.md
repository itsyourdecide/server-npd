# План пользовательской платформы server-npd

Статус: актуальный план
Дата создания: 2026-09-05
Последняя редакция: 2026-09-05
Живая проверка при подготовке: не выполнялась
Источник истины для: состава и последовательности реализации пользовательского портала

## Назначение

Существующая инфраструктура предоставляет Proxmox, HTCondor, PXE, CVMFS,
мониторинг и SSH-доступ, но ещё не образует самостоятельный пользовательский
сервис. Цель этого плана - создать единый портал, через который пользователь
может получить доступ, работать с проектами, отправлять задания, запрашивать VM
и отслеживать состояние своих запросов.

Статус конкретных работ хранится в [открытых задачах](open-issues.md), а
фактическое состояние развёрнутых компонентов - в
[текущем состоянии](../current-state.md).

## Ожидаемый пользовательский результат

Пользователь должен иметь возможность:

- узнать возможности кластера и правила работы;
- зарегистрироваться и подать заявку на доступ;
- создать проект или запросить вступление в существующий;
- увидеть доступные ресурсы и свои квоты;
- отправить HTCondor-задание;
- наблюдать очередь, состояние, логи и результаты;
- остановить или повторить своё задание;
- запросить создание или продление VM;
- отправить запрос на программное обеспечение, сеть или восстановление данных;
- получить уведомление об изменении статуса;
- открыть пользовательскую документацию.

Администратор должен иметь возможность:

- рассматривать заявки;
- назначать роли и квоты;
- согласовывать или отклонять запросы;
- контролируемо создавать ресурсы;
- видеть журнал действий;
- блокировать пользователя или проект;
- восстанавливать состояние по базе данных и журналам.

## Границы системы

Публичный сайт и портал разделяются логически:

- публичная часть содержит описание, правила, обезличенное состояние и
  документацию;
- портал требует входа и показывает данные конкретного пользователя;
- административная часть доступна только операторам;
- Proxmox, IPMI и внутренние сервисы не публикуются напрямую в интернет.

## Целевая архитектура

```text
Пользователь
     |
   HTTPS
     |
Nginx / reverse proxy
     |
     +-- публичный сайт и документация
     |
     +-- пользовательский портал
            |
            +-- Keycloak: вход, роли, 2FA
            +-- PostgreSQL: проекты, заявки, квоты, аудит
            +-- фоновый worker
                    |
                    +-- HTCondor API
                    +-- Proxmox API
                    +-- Ansible
                    +-- уведомления
```

## Предлагаемый технологический состав

- Django как основное серверное приложение;
- серверные HTML-шаблоны и HTMX для интерактивных элементов;
- PostgreSQL как источник истины портала;
- Keycloak и OpenID Connect для входа и ролей;
- отдельный фоновый worker для операций с инфраструктурой;
- Nginx как reverse proxy и точка завершения TLS;
- MkDocs для публикации пользовательской документации;
- Prometheus, Grafana и централизованные логи для сопровождения портала.

На первом этапе отдельный SPA и набор микросервисов не требуются. Монолитное
приложение уменьшает число компонентов и ускоряет получение первой рабочей
версии.

## Модель данных

Минимальный состав PostgreSQL:

| Сущность | Назначение |
|---|---|
| `users` | профиль пользователя и связь с внешней идентификацией |
| `projects` | исследовательский или учебный проект |
| `project_members` | членство и роль в проекте |
| `access_requests` | заявки на доступ |
| `resource_requests` | общий реестр запросов ресурсов |
| `approvals` | решения, комментарии и согласующие лица |
| `quotas` | ограничения проекта или пользователя |
| `job_runs` | связь портала с заданиями HTCondor |
| `vm_requests` | параметры запрошенных VM |
| `vm_instances` | созданные VM и их состояние |
| `notifications` | события доставки уведомлений |
| `audit_events` | неизменяемый журнал значимых действий |

Каждая пользовательская сущность принадлежит пользователю или проекту. Доступ
проверяется на уровне приложения; дополнительная защита строк PostgreSQL может
быть добавлена после стабилизации модели прав.

## Роли

- `user` - работает только со своими ресурсами и проектами;
- `project_lead` - управляет участниками и квотами своего проекта;
- `reviewer` - рассматривает заявки;
- `operator` - выполняет инфраструктурные операции;
- `admin` - управляет платформой и политиками.

Роль портала не должна автоматически давать административные права в Proxmox,
HTCondor или ОС.

## Жизненный цикл заявки

```text
черновик
  -> отправлено
  -> рассматривается
  -> согласовано
  -> выполняется
  -> активно
  -> завершено

Дополнительные состояния:
отклонено / ошибка / отменено / истекло
```

Каждый переход содержит время, автора, комментарий и технический результат.

## Типы заявок

- доступ к кластеру;
- создание проекта;
- вступление в проект;
- увеличение квоты;
- создание или продление VM;
- открытие сетевого доступа;
- установка программного обеспечения;
- публикация набора данных;
- восстановление данных;
- техническая проблема.

<a id="u0"></a>
## Этап U0 - архитектурные решения и границы безопасности

До разработки нужно зафиксировать ADR для:

- выбора Django и границ монолита;
- использования Keycloak/OIDC;
- связи пользователя портала с Unix UID и владельцем HTCondor-задания;
- правил доступа worker к Proxmox и HTCondor;
- хранения загружаемых файлов;
- удаления, архивации и срока хранения пользовательских данных.

Критерий готовности:

- определена модель доверия;
- секреты worker не доступны веб-процессу и пользователю;
- описаны резервное копирование и восстановление PostgreSQL.

<a id="u1"></a>
## Этап U1 - основа портала

Создать `portal01` или эквивалентное изолированное размещение и развернуть:

- Django;
- PostgreSQL;
- Nginx и TLS;
- Keycloak или подключение к отдельному Keycloak;
- OIDC-вход;
- базовые роли;
- проверку состояния и мониторинг;
- резервное копирование базы данных.

Критерий готовности:

- пользователь входит через OIDC;
- закрытые страницы недоступны без входа;
- база восстанавливается из тестовой резервной копии;
- административные действия журналируются.

<a id="u2"></a>
## Этап U2 - проекты и заявки

Реализовать:

- профиль пользователя;
- создание проекта;
- членство и роли проекта;
- заявки на доступ и ресурсы;
- очередь рассмотрения;
- согласование, отклонение и комментарии;
- историю состояний;
- административную панель;
- уведомления о смене статуса.

На этом этапе согласованная заявка ещё может исполняться администратором
вручную. Это позволяет проверить процесс до автоматизации инфраструктуры.

Критерий готовности:

- заявка проходит полный путь от пользователя до решения;
- пользователь видит только свои проекты и заявки;
- оператор видит очередь и журнал решений.

<a id="u3"></a>
## Этап U3 - публичный сайт и документация

Опубликовать:

- описание проекта и доступных возможностей;
- правила использования;
- требования к заявке;
- примеры HTCondor-заданий;
- пользовательскую документацию;
- контакты и порядок поддержки;
- обезличенное состояние сервисов;
- ссылку на вход и регистрацию.

В публичную сборку не попадают внутренние IP, MAC-адреса, имена закрытых
узлов, ключи, токены и административные инструкции.

<a id="u4"></a>
## Этап U4 - просмотр и отправка HTCondor-заданий

Первая форма отправки содержит:

- название и проект;
- исполняемый файл или утверждённый шаблон;
- аргументы и входные файлы;
- число CPU;
- объём RAM и диска;
- максимальное время;
- число повторений;
- каталог результатов.

После отправки портал показывает:

- `ClusterId` и `ProcId`;
- состояние и причину удержания;
- время ожидания и выполнения;
- рабочий узел;
- stdout, stderr и журнал событий;
- использованные ресурсы;
- действия остановки и повторного запуска.

Интеграция выполняется через актуальные Python bindings HTCondor и
`Schedd.submit()`. Для удалённой отправки и управления применяются отдельные
учётные данные с минимальными правами. Пользователь портала должен однозначно
соответствовать владельцу задания HTCondor.

Первая версия разрешает только проверенные профили:

- тестовое задание;
- Python;
- shell batch;
- ROOT;
- Geant4;
- массив однотипных заданий.

Критерий готовности:

- пользователь отправляет, просматривает и останавливает только свои задания;
- лимиты проверяются до передачи задания в HTCondor;
- действия и идентификаторы HTCondor записываются в аудит;
- результаты доступны только владельцу и участникам его проекта.

<a id="u5"></a>
## Этап U5 - заявки на VM

Первая версия не создаёт VM автоматически. Пользователь указывает:

- проект и назначение;
- шаблон ОС;
- CPU, RAM и диск;
- требуемую сеть;
- срок действия;
- список участников.

После согласования оператор создаёт VM вручную, а портал хранит её VMID,
владельца, срок действия и состояние.

Критерий готовности:

- VM связана с проектом и согласованной заявкой;
- превышение квоты невозможно согласовать случайно;
- приближение срока окончания создаёт уведомление.

<a id="u6"></a>
## Этап U6 - автоматическое создание VM

После проверки ручного процесса фоновый worker получает возможность:

- клонировать только утверждённые шаблоны;
- применять cloud-init;
- назначать VM в resource pool проекта;
- применять согласованные CPU, RAM, диск и VLAN;
- выдавать ограниченные ACL;
- блокировать, продлевать или удалять ресурс по политике.

Worker использует отдельный Proxmox API token с минимальными правами. Полный
административный токен и `root@pam` запрещены.

Критерий готовности:

- повторная обработка запроса не создаёт вторую VM;
- каждая операция имеет журнал и возможность безопасного отката;
- пользователь не может выйти за пределы resource pool и квоты проекта;
- удаление требует отдельного подтверждения и проверенной резервной копии.

<a id="u7"></a>
## Этап U7 - эксплуатационная зрелость портала

Добавить:

- Alertmanager и уведомления об ошибках портала и worker;
- панели Grafana;
- централизованные журналы;
- ограничение частоты запросов;
- проверку загружаемых файлов;
- срок хранения логов и результатов;
- регулярную очистку истёкших сессий и временных файлов;
- тесты восстановления PostgreSQL;
- журнал административных действий;
- регламент обновлений и аварийную инструкцию.

## Возможности после первой стабильной версии

- JupyterHub или другая интерактивная среда;
- web terminal с ограниченным доступом;
- пользовательские базы данных по заявке;
- каталог программного обеспечения и готовых профилей;
- публикация наборов данных;
- API или CLI для автоматической отправки;
- интеграция с университетским LDAP/AD;
- интеграция с DIRAC/LHCb;
- отдельный Slurm/MPI-сервис при подтверждённой потребности.

## Обязательная последовательность

1. Архитектурные решения и модель безопасности.
2. Django, PostgreSQL, Keycloak, Nginx и резервное копирование.
3. Пользователи, проекты и ручной процесс заявок.
4. Публичный сайт и пользовательская документация.
5. Просмотр HTCondor и отправка тестовой задачи.
6. Полное управление своими заданиями и квотами.
7. Ручное исполнение заявок на VM.
8. Автоматизация VM через ограниченный Proxmox API token.
9. Уведомления, аудит и эксплуатационные проверки.
10. Интерактивные и дополнительные сервисы.

## Что не делать в первой версии

- не предоставлять веб-приложению `root@pam`;
- не отправлять все задания от одного неразличимого владельца;
- не позволять пользователю передавать произвольные ClassAd без проверки;
- не открывать Proxmox или IPMI напрямую в интернет;
- не создавать VM без квоты, срока действия и владельца;
- не автоматизировать процесс, который ещё не прошёл ручную проверку;
- не хранить секреты в PostgreSQL открытым текстом;
- не строить микросервисную архитектуру без подтверждённой нагрузки.
