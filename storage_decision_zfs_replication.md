# Решение по хранилищу: ZFS-репликация вместо Ceph (основной путь)

Версия: 1.0
Дата: 2026-07-02
Статус: принятое решение, пересматривает раздел 8 `cluster_architecture_rationale.md` и раздел 4 `cluster_architecture_presentation.md`

## 1. Решение

Ceph **не рассматривается как основной путь** к отказоустойчивому хранилищу VM. Основной путь — **встроенная в Proxmox ZFS-репликация** между узлами.

Ceph не отменяется навсегда — это осознанная пауза, а не отказ от идеи. Условие пересмотра см. в разделе 5.

## 2. Почему

Ceph требует выделенную сеть минимум 10GbE (см. `cluster_architecture_rationale.md`, 8.3) — иначе recovery/backfill мешает Corosync и создаёт риск потери quorum, а восстановление даже одного упавшего 6TB-диска на 1GbE занимает 15+ часов.

Бюджет на сетевое оборудование под Ceph — **5000 грн (~$112)**. Проверены реальные цены: дешевле $699 (MikroTik CRS312-4C+8XG-RM, 12 портов) готового 10GbE-свитча с нужным числом медных портов не нашлось, и даже 3-4-портовых дешёвых вариантов на рынке практически нет (см. переписку 2026-07-02, зафиксировано в `production_port_plan.md`, разделы 4.1-4.2). Вариант с full mesh для 3 core-узлов (без свитча) требует докупки третьей сетевой карты на каждый из 3 узлов и усложняет эксплуатацию.

Решение: не подгонять архитектуру под ограничение бюджета костылями (урезанный mesh, самодельная схема на грани), а выбрать путь, которому 10GbE вообще не нужен.

## 3. Что даёт ZFS-репликация и чем она отличается от Ceph

| | Ceph | ZFS-репликация |
|---|---|---|
| Сеть | Нужна выделенная 10GbE | Хватает существующего 1GbE |
| RPO при отказе узла | Близко к нулю | До интервала репликации (типично 5-15 минут, настраивается) |
| Доп. железо | 10GbE-свитч или сетевые карты под mesh | Не требуется |
| HA для дисков VM (перезапуск на другом узле) | Да | Да |
| Общая файловая система для нескольких узлов одновременно (аналог CephFS, нужно для общих данных HTCondor/пользователей) | Да | **Нет** — репликация это копия, не общий доступ |
| Сложность эксплуатации | Выше | Ниже |

Механизм: диск VM живёт на локальном ZFS (зеркало двух системных SSD, уже так и планировалось), Proxmox периодически досылает изменения (снапшот-based) на один или несколько других узлов. При отказе исходного узла HA поднимает VM на узле с последней доступной репликой.

## 4. Что остаётся открытым вопросом (не решено этим документом)

- **Общая файловая система** для данных HTCondor/пользовательских проектов — раньше это была роль CephFS. Без Ceph нужен другой путь: вероятно, отдельный NFS-сервер поверх ZFS-пула. Но такой сервер сам становится точкой отказа, если его не резервировать отдельно (либо смириться с этим для первого этапа, либо решать отдельно позже).
- **Судьба уже проверенной JBOD-полки** (24 диска, все здоровы, см. `cluster_operations_log.md`, запись 2026-07-02) — работа не потеряна. Диски можно использовать под большой ZFS-пул для bulk/архивных данных на одном узле (аналог класса "Archive"/"Backup" из `cluster_architecture_presentation.md`, раздел 4.3) — без live-HA для этих данных конкретно, но с отдельным бэкапом. Это отдельная задача на потом — "думать, как сделать это хорошо", по формулировке пользователя, а не решённый вопрос.
- Точная схема сети для трафика самой ZFS-репликации не выбрана — скорее всего можно пустить по существующему транку (`vmbr2`/порт 4) на отдельном VLAN, специальное 10GbE тут не нужно, но конкретный VLAN/маршрут не назначен.

## 5. Условие пересмотра (когда возвращаемся к Ceph)

- Появляется бюджет на нормальный 10GbE-свитч (или находится рабочий б/у вариант — у проекта уже есть опыт работы со списанным оборудованием CERN), **или**
- Реальная нагрузка показывает, что ZFS-репликации недостаточно (например, нужен zero-RPO для конкретного сервиса, или нужна настоящая общая POSIX-файловая система с производительностью, которую NFS не тянет).

До этого момента Ceph-специфичные пункты в других документах (VLAN 60/61, раскладка портов под Ceph-свитч, Этап C в `cluster_implementation_plan.md`) считаются **отложенными**, не удалёнными — оставлены для быстрого возврата, если условие пересмотра наступит.
