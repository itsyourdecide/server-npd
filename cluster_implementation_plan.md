# План внедрения кластера

Версия: 1.1  
Дата: 01.07.2026  
Основа: `cluster_architecture_presentation.md`

> **Это единственный источник по поэтапному порядку внедрения (Этапы A–G).** Обзорные документы (`cluster_architecture_presentation.md` §11, `cluster_architecture_rationale.md` §14) только ссылаются сюда, чтобы копии плана не расходились. Порядок именно лабораторной сборки — в `cluster_lab_poc_plan.md`.

Лабораторный стенд выполняется по `cluster_lab_poc_plan.md`.

## Принцип

Каждый этап должен завершаться работающим и проверяемым состоянием. Production-данные не загружаются до проверки отказа, восстановления и backup.

## Этап A — инвентаризация и проектирование

Результат: подтверждённые BOM и topology.

- выполнить `cluster_inventory_checklist.md`;
- сохранить конфигурацию `head01` и HP;
- выбрать три одинаковых Supermicro;
- определить SAS и 10GbE topology;
- измерить питание;
- составить минимальный список закупок.

Стоп-критерии: отсутствуют HBA/кабели, диски имеют массовые SMART-ошибки, нет подходящей сети для пилота.

## Этап B — Proxmox pilot

Результат: трёхузловой кластер с устойчивым quorum.

1. Сделать backup конфигурации Ubuntu `head01`.
2. Обновить BIOS/BMC только по отдельному проверенному плану.
3. Установить одинаковую поддерживаемую версию Proxmox VE на три узла.
4. Использовать ZFS mirror из двух локальных SSD, если они исправны.
5. Настроить DNS/NTP и статические management IP.
6. Создать кластер `department-pve`.
7. Выделить Corosync network; не смешивать её с трафиком репликации хранилища.
8. Проверить потерю одного линка и выключение одного узла.
9. Настроить ZFS-репликацию тестовой VM между узлами (основной путь к HA-хранилищу, см. `storage_decision_zfs_replication.md`), проверить HA-перезапуск на узле с актуальной репликой после отказа исходного.

Текущий факт на 01.07.2026:

- `pve01` уже установлен и поднят в лабораторной сети как временный шаг для удалённого доступа;
- удалённый доступ через Tailscale включён;
- все изменения по ходу пилота фиксируются в `cluster_operations_log.md`;
- перед созданием production-подобной сетевой схемы `pve01` нужно вернуть с временной лабораторной адресации на целевой management-plan.

Не устанавливать пользовательские production-VM на этом этапе.

### Лабораторный routing/firewall PoC

- общий лабораторный router не перенастраивается;
- Switch 1 получает uplink через временный access VLAN 99;
- OPNsense VM получает WAN по DHCP в VLAN 99;
- внутренние VLAN используют постоянный план `10.10.<VLAN>.0/24`;
- проверяются NAT, DHCP, firewall, DMZ и port forwarding;
- перед production VLAN 99 и двойной NAT удаляются.

## Этап C — Ceph pilot (отложено 2026-07-02)

**Отложено:** основной путь к HA-хранилищу теперь ZFS-репликация, не Ceph — см. `storage_decision_zfs_replication.md`. Причина — бюджет не покрывает нужную для Ceph выделенную 10GbE-сеть. Этот этап актуален при пересмотре решения (появление бюджета/б-у 10GbE-оборудования, или недостаточность ZFS-репликации под реальную нагрузку). До тех пор HA-VM проверяется через ZFS-репликацию в рамках Этапа B/D.

Результат: RBD shared storage и тестовая HA-VM.

1. Подключить отдельную JBOD к каждому PVE-узлу.
2. Выполнить SMART/burn-in выбранных HDD.
3. Ввести 3–4 OSD на host.
4. Разместить MON на трёх узлах, MGR минимум active/standby.
5. Создать replicated RBD pool `size=3`, `min_size=2`.
6. Создать тестовую VM на RBD.
7. Проверить live migration.
8. Имитировать отказ HDD, полки и одного PVE-узла по отдельности.
9. Измерить latency, throughput и время recovery.

Стоп-критерий: Ceph recovery нарушает Corosync/quorum или заполняет сеть.

## Этап D — базовая платформа

Результат: управляемый сервис для первых пользователей.

- два локальных администратора с отдельными аккаунтами и MFA;
- Tailscale/WireGuard на PVE-хостах;
- HA bastion с SSH key-only;
- HA reverse proxy;
- firewall и начальная VLAN-сегментация;
- monitoring, central logs и alerts;
- Linux cloud-init template;
- роли, квоты и жизненный цикл временных VM;
- первая backup-система и тест восстановления.

## Этап E — первые пользователи

Результат: несколько персональных Linux VM.

- VM создаёт администратор;
- пользователь получает sudo внутри VM;
- VM имеет исходящий интернет;
- входящий интернет закрыт;
- SSH выполняется через bastion;
- web публикуется только через reverse proxy по заявке;
- критические VM включены в Proxmox HA;
- постоянные и временные VM помечены тегами и имеют владельца.

## Этап F — HTCondor pilot

Результат: execute VM на Supermicro и несколько bare-metal ASUS выполняют тестовые Geant4/ROOT jobs в одном HTCondor pool.

1. Выбрать один-два исправных ASUS chassis.
2. Настроить PXE/autoinstall.
3. Развернуть HTCondor Central Manager и Submit node как HA-VM/LXC.
4. Подключить compute к CephFS.
5. Проверить file transfer, retry, fair-share и большое число независимых jobs.
6. Проверить checkpoint и повторный запуск.
7. Сначала включить alerts, затем ручное IPMI power control.
8. Автоматический power saving вводить последним. Slurm рассматривается отдельно только при подтверждённой потребности в многонодовом MPI/HPC.

## Этап G — production и расширение

- получить/настроить публичный uplink или VPS tunnel;
- запросить DNS-поддомен;
- согласовать LDAP/AD;
- расширить Ceph только проверенными дисками;
- создать archive pool после выбора EC profile;
- добавить независимый backup;
- добавить `pve04–pve10` в общий кластер по одному после проверки мощности, охлаждения и quorum;
- масштабировать питание и охлаждение по измерениям;
- провести документированный failover и thermal drill.

## Что не делать

- не выключать массово участников десятиузлового PVE-кластера: при 10 голосах quorum равен 6;
- не выключать Ceph OSD-хосты через HTCondor/Slurm power automation;
- не использовать единый VLAN для IPMI, пользователей и public services;
- не считать Ceph резервной копией;
- не публиковать Proxmox/IPMI в интернет;
- не запускать автоматический hard power-off без испытаний;
- не покупать сетевые/HBA-компоненты до инвентаризации склада.
